## 2026-11-14 -- GitHub: a failed read of github-config.json no longer wipes the saved accounts (planning #307, lead B15)

**Problem.** `github-config.json` holds the saved GitHub accounts next to the GitHub settings. The store answered a read that failed (another program held the file, the text was not JSON, a newer build wrote it) with "no config", the same as no file at all. Every writer took that for a first run, started from the defaults and saved them: one read that failed for a moment, and the next change (a toggle, a new account, the onboarding stamp) replaced every saved account with the defaults plus that one change. Two more faults sat beside it. A save over an existing file copied over it in place, so a save that failed part way could leave half a file, which the next read then took for "no config". And the settings patch read and wrote the file outside the lock the account edits use, so a setting and an account edit made at the same moment could each save over the other; the start-up migration did the same.

**Change.**
- `src/main/github/github-config-store.ts`: one read (`load`) tells "no file" from "did not read". `read()` is for callers that only read and still answers null for both, so the panel renders as before. `readForWrite()` is new and is what a writer starts from: null only when there is no file yet, and `GitHubConfigUnreadableError` for a file that is there but did not read. Its message is one fixed sentence that names the file and never its folder.
- `write()` now goes through the shared atomic write (`src/main/atomic-write.ts`): staged under a random name beside the file, renamed over it, with the short retry Windows needs. A save that fails part way removes its staging file and leaves the old file whole.
- `src/main/github/auth/auth-profile-store.ts`: every writer (add, remove, update, rotate token, the same-account replace) reads with the strict read. `editConfig` is new: a whole-file change under the same lock as the account edits.
- `src/main/ipc/github-handlers.ts`: the settings patch (`GITHUB_CONFIG_UPDATE`) and the start-up migration go through `editConfig`, so every change to the file takes the one lock. The account channels answer a file that did not read with `{ ok: false, error: <the sentence> }`; the settings patch, which answers the config itself, rejects with it. Nothing is written in either case.
- A byte-order mark an editor put before the text is passed over, as `profiles.json` already does.
- An unknown-schema file is no longer replaced, so it stays and is read again and again. It is backed up once per run for the same text, instead of once per read (which would have pushed older backups out of the three that are kept).

**What the user sees.** A refused change on the GitHub settings page shows one red line under the page title with the sentence, and the control stays as it was; the line goes when the next change starts. The add-account dialogs, the device sign-in and the onboarding GitHub step show the same sentence in the error slot they already had. `src/renderer/stores/githubStore.ts` keeps the reason (`saveError`) and treats an `{ ok: false }` answer to remove, rename and a feature toggle as the failure it is; before, those answers were not looked at.

**Kept.** No file still starts from the defaults (first run). What a reader gets is unchanged, apart from the byte-order mark. The file's mode is what it was.

**The cost.** A file that stays unreadable (cut short by an old crash, hand-edited into bad JSON, written by a newer build) is no longer healed by being overwritten. GitHub then shows no accounts and refuses every change, naming the file, until the file is repaired or removed. That is the intended side: the accounts in it are still there.

**Not in this change.** The page does not say on opening that the file did not read; it shows the defaults and says so only when a change is refused. A read that fails once at start-up is still remembered as "no config" by the sync's own cache until a save goes through or the app restarts. Two copies of the app writing one resources folder are not serialised (the lock is inside one process).

**Tests.** `tests/unit/main/github-config-never-wiped.test.ts` (new) drives the real handlers and stores on a temporary folder: for five ways the file can fail to read, each of the seven channels that write it is refused and the file is the same byte for byte; a refused change goes through once the file reads again, on top of every earlier account; a save that fails at the replace step leaves the old file whole and nothing staged; no file still starts empty; a setting and an account edit sent together, in three orders and six at once, keep every change; the start-up migration and a setting sent as the app starts keep both. 44 of its 51 cases failed before the change. `tests/unit/github/github-config-store.test.ts` and `tests/unit/github/auth-profile-store.test.ts` hold the same rules at the store level, and `tests/unit/github/githubStore.test.ts` the renderer's.
