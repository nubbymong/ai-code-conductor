## 2026-11-14 -- GitHub: github-config.json is never replaced by defaults, the rule profiles.json follows (planning #307, lead B15)

**What this does.** `github-config.json` holds the saved GitHub accounts next to the GitHub settings. It follows the rule `profiles.json` follows for the Claude accounts (PR #657): a file that is there but did not read is refused and left byte for byte; a writer starts from the defaults only when there is no file; the save is the same `atomicWriteSecure` write; and the user is told in one fixed sentence that names the file and never its path. The sentence also says what to do next: close other programs that may be using the file, or move it out of the CONFIG folder in the resources folder and sign in to GitHub again. It lives once, in `src/shared/github-constants.ts`, for main (which refuses with it) and the settings pages (which show it).

**The read** (`src/main/github/github-config-store.ts`).
- One read (`load`) tells "no file" from "did not read". `read()` answers null for both, for callers that only show what is there. `readForWrite()` answers null only for no file and raises `GitHubConfigUnreadableError` for a file that did not read. `readState()` answers `{ config, readFailed }` for the callers that have to tell the two apart.
- "No file" takes two answers. After a read says there is no such file, the path is looked at once more; a file that is there after all, or a path that cannot be looked at, is a read that failed.
- A file with nothing in it (no bytes, or only a byte-order mark, white space and NUL characters) is "no file". It holds no account, so a refusal would protect nothing, and a write cut off by a power loss can leave one. The first write replaces it. A file with text in it that is cut short stays unreadable.
- "Nothing in it" takes two answers as well. After a read gives nothing, the file is read once more, and only the same nothing a second time is "no file"; text that is there after all, a different length, or a second read that fails, is a read that failed.
- A byte-order mark an editor put before the text is passed over, as `profiles.json` does.
- The log line for a read that failed carries the error's name and code, or "not valid JSON". It never carries the error's own text: a JSON error quotes the characters around the place it stopped, which in this file can be a token's ciphertext. Each kind of failure is logged once until a read succeeds, however often the file is read meanwhile; a copy of an unknown-schema file that cannot be made is logged the same way.
- A file from a version this build does not know stays where it is and is backed up once per run for the same text. The copy is created exclusively and for the owner alone (0600).

**The write.**
- `write()` goes through `atomicWriteSecure` (`src/main/account-profiles.ts`, over `src/main/atomic-write.ts`) with mode 0600, the mode `config-manager` passes for its secret files: the new bytes are staged beside the file under a random name, created exclusively and for the owner alone, and renamed over it, with the bounded retry for a rename another program refuses for a moment. On macOS and Linux the file that results is 0600 whatever mode the file it replaces had; that mode is not read or carried over. Windows has no such modes.
- A write that fails removes its staged copy and leaves the old file whole. It is raised as `GitHubConfigWriteError`, whose message is a second fixed sentence (the file could not be saved, nothing was changed). What failed, with its path, goes to the log in main and is never handed to the renderer.

**The writers** (`src/main/github/auth/auth-profile-store.ts`, `src/main/ipc/github-handlers.ts`, `src/main/github/github-settings-patch.ts`).
- Every change to the file takes one lock and starts from the strict read: the account edits, the settings patch and the start-up migration (`editConfig`). A setting and an account edit made at the same moment keep both.
- A device sign-in for an account that is already saved adds the new profile and removes the earlier one in ONE read and ONE write (`addProfile(..., { replaceSameAccount: true })`), carrying that account's feature toggles over. A read that fails refuses the whole sign-in with nothing written. The flow is ended as soon as its code is spent, whichever way the sign-in ends.
- `GITHUB_CONFIG_UPDATE` takes the settings only: `enabledByDefault`, `transcriptScanningOptIn`, `seenOnboardingVersion`, and the sub-maps `syncIntervals`, `appWideToggles` and `featureDefaults`, each merged key by key onto the map in the file. `schemaVersion`, `authProfiles`, `defaultAuthProfileId` and any other key are left out, as is a value of the wrong kind. A patch with no setting in it saves nothing.
- The account channels answer both refusals with `{ ok: false, error: <the sentence> }`. The settings channel, which answers the config itself, rejects with the sentence.
- A removal that was refused removes nothing, so the sessions bound to that account are not read or saved.
- The config cache the sync, the notifications, the AI-usage meter and a re-authorization read through keeps only an answer that was read (the config, or "no file yet"). A read that failed is never kept as "no accounts". It stands in for the lookups the timers make (every sync tick of every session, the notifications, the meter, the session-context panel's poll) for 30 seconds (`lookupState`, `FAILED_READ_HOLD_MS`), so a file that stays unreadable is read once per hold and not once per lookup; then it is read again. Any read that succeeds in between, by a settings page or a save, ends the hold at once.
- A button the user pressed does not wait for that hold: re-authorize, merge, re-run, mark ready, reply, the two "Sync now" buttons, Refresh on the AI-usage meter and turning GitHub on for a session read the file now. So a saved account can be re-authorized as soon as the file reads.

**The settings pages** (`src/renderer/stores/githubStore.ts`, `src/renderer/components/github/config/`, `src/renderer/onboarding/GitHubStep.tsx`).
- `GITHUB_CONFIG_GET`, asked with `{ readState: true }` (which is what the bridge's `getConfig` sends), answers `{ config, readFailed }`. Not asked, it answers the config or null.
- The store marks a read that failed (`configUnread`). With nothing read before, it shows the defaults so the page renders, and the page shows the sentence as it opens. Settings an earlier read gave stay on show. While the mark is set, every save reads the file again first and is refused, with the sentence, if it still does not read; so no change is built from defaults that stood in for settings that were not read.
- A change to one key of a sub-map is sent as that key: an app-wide toggle, a sync interval, and the feature default that follows a toggle on the only account.
- The set-up page's Next saves its version stamp, and the GitHub master only when the user set it on that page or the value shown was read from the file. Next waits for that save. A save that was refused is shown on the page in the store's sentence and the page stays, so a choice made there is not dropped without a word; "Skip for now", offered from then on, moves on with nothing saved. A page left with Back while the save is on its way is not moved on.
- A feature toggle is up to two saves (the account, then the defaults). The config is read again whichever way it ends.
- A refused change shows one red line under the page title; the line goes when the next change starts. A control that starts a save hands it to `quietly`, so a refused save is not left as an unhandled rejection. The add-account dialogs, the device sign-in and the set-up page show the sentence in the error slot they have. The device sign-in stops saying it is waiting once it has an error, and a token submit clears the error an earlier sign-in attempt left.

**The cost.** A file that stays unreadable (text cut short, hand-edited into bad JSON, written by a newer build) is not healed by being overwritten. GitHub then shows no accounts and refuses every change until the file is repaired or moved out, which the sentence says. The accounts in it are still there. After a read that failed, the lookups the timers make can go up to 30 seconds without the saved settings and accounts once the file reads again, unless a page, a save or a pressed button reads it sooner.

**Not in this change.** Two copies of the app writing one resources folder are not serialised: the lock is inside one process.

**Tests.**
- `tests/unit/main/github-config-never-wiped.test.ts` drives the real handlers and stores on a temporary folder. For five ways the file can fail to read, each of the seven channels that write it is refused and the file is the same byte for byte. A save that fails while staging or while replacing is answered the second sentence on each of the seven channels, with the old file whole and nothing staged left behind. A refused change goes through once the file reads again. No file, and a file with nothing in it, start empty. A setting and an account edit sent together, in three orders and six at once, keep every change, as do the start-up migration and a setting sent as the app starts. A settings patch changes settings only, and one key of a sub-map changes that key only. A device sign-in whose read fails leaves the file unchanged, and one that goes through leaves it fully changed. A refused removal leaves the session bindings alone. A read that failed as the app started is not remembered. The timers' lookups read a file that stays unreadable once per hold, with one log line, and have the accounts back after the hold or as soon as anything reads the file; each button the user can press reads it now. Through the renderer's own store, a page opened while the file did not read refuses every change while it still does not read, and once it reads again changes the one value and keeps every other value in the file.
- `tests/unit/github/github-config-store.test.ts` holds the read (with the second look at "no file" and at "nothing in it"), the hold on a failed read, the once-per-kind log line, the write, the retry of a refused rename and the owner-only mode at the store level; the three cases that read a real mode from disk run on macOS and Linux only. `tests/unit/github/auth-profile-store.test.ts` holds the writers and the one-write sign-in.
- `tests/unit/github/githubStore.test.ts` and `tests/unit/github-feature-actions.test.ts` hold the renderer store. `tests/unit/renderer/github-settings-refusal-ui.test.tsx`, `tests/unit/renderer/account-panel.test.tsx` and `tests/unit/renderer/github-config-tab.test.tsx` hold the pages and the dialogs, with the set-up page's Next and "Skip for now", and the settings page opened on defaults that stand in for a file that did not read.
