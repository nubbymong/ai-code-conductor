## 2026-11-17 -- Statusline ticks that change nothing are skipped, and one listener serves every session (2.1.3-beta.7, plan section B2)

**What.** aicc_planning#304, renderer only. Three changes:
- `updateSession` compares plain objects and arrays by value (`sameStatusValue`, the guard from PR #654, which was never merged and is superseded by this change). A statusline tick hands it `usageBuckets` and `rateLimitExtra` as fresh objects from IPC, so the old `!==` check called every tick a change, replaced the `sessions` array, and re-rendered everything that reads the whole array (the multi-account footer among them) on every tick from every session. Anything that is not a plain object or array is still compared by identity, and past depth 6 a value counts as changed.
- `RateLimitBar` is wrapped in `React.memo`. Its props are primitives, so a bar whose figures did not change skips its render, and with it the `formatResetTime` calls that B1 found to be the renderer's top self-time function at N=25 busy on beta.6. Its reset text also depends on today's date (a reset later today shows the time only), so the bars also render at local midnight: one timer for all of them, set while any bar is on screen (raised in review: without it a reset dated tomorrow kept its date after midnight until the bar's figures changed).
- `src/renderer/lib/sessionBroadcastRouter.ts`: the statusline, effort, watchdog and account-identity channels each have one preload listener for all sessions. Each TerminalView used to add its own listener per channel, so with N sessions every message crossed the context bridge N times and N-1 handlers threw it away. The router hands a message only to the handlers of its own session, drops one whose session has no handler, and releases the channel on the last unsubscribe.

**Decisions.**
- A session id holds a set of handlers, not one: during a remount handover the old and the new view of a session can both be subscribed for a moment, and each keeps its own unsubscribe.
- The router binds again when the bridge's `onUpdate` function changes, releasing the old listener first. In the app it never changes; a test that installs a fresh `window.electronAPI` mock, or a dev hot reload, does. Without this, the existing hook tests that leave a hook mounted would keep the first test's mock bound.
- The four hooks no longer check the session id themselves: the router does, and its tests prove it.
- No preload, IPC or main change, so no adversarial pass, and nothing in the SSH live-matrix radius.

**Measured on the test VM** (2026-11-17, B1's harness at 58a5e7e0, one run each, shortened: N=25 only, 60 s idle settle, 60 s windows, 5 min busy settle, 90 s renderer profiles, no A/B/A, no ablations). Before: the installed 2.1.3-beta.6. After: this branch at 58a5e7e0 (its first commit; the midnight timer came later and was not measured), built on the VM with `electron-builder --dir` without the session helper binary (off by default) and started through `CCC_STAGE_APP_EXE`.
- 90 s renderer profile at N=25 busy: `RateLimitBar` 30.3 ms self and 788.8 ms inclusive before, 0.0 and 59.4 after; `formatResetTime` self 754.4 and 59.4 ms. At N=25 idle, `RateLimitBar` inclusive 53.1 and 5.1 ms. The preload `handler` (one call per listener per message) 1.20 and 0.61 ms per second busy, 0.16 and 0.07 idle.
- Renderer CPU, % of one core: 24.87 and 23.62 busy, 3.36 and 3.37 idle; renderer main thread busy (CDP task time) 16.7 and 15.4 % busy. One run each, inside the 1.3 to 2 point spread B1 saw between all-on runs, so no CPU gain is claimed.
- The plan's acceptance (`RateLimitBar` under 50 ms self in a 90 s profile at N=25; 333 ms on 2.1.2) was already met on beta.6: 30.3 ms here, 17.8 and 14.1 ms in B1's 60 s profiles.
- The fake CLI recomputes its reset times from the clock on every status write, and its cost, tokens and duration grow every tick, so on the VM every tick really changes its session and the store guard skips little; on Claude Code the reset times stay fixed between ticks. The drop in `formatResetTime` is most likely the memo (a bar now renders when the session it shows ticks, not when any of the 25 does); the run does not separate the guard from the memo.

**Tests.** `tests/unit/renderer/session-store-noop-ticks.test.ts` (7 cases: the guard from #654, a render check on the memoized bar, and the bar at local midnight on a fake clock) and `tests/unit/renderer/session-broadcast-router.test.ts` (7 cases). Before the change the store file failed 4 of its first 6 cases (the equal-values case on its assertion, the two `sameStatusValue` cases because the export did not exist, the bar case on its assertion) and the router file failed to load (the module did not exist); the midnight case came with the review fix. Each of the 14 cases was then seen red under at least one of ten mutants, each run on the two files through the locked runner: guard back to `!==`; router delivering to every session; the beta hooks restored with the router present (25 listeners per channel); no release on the last unsubscribe; bar not memoized; non-plain objects compared by value; release that forgets the listener; no rebind on a new bridge; any two arrays equal; bar not woken at midnight. Two test faults the mutants exposed, both fixed: the StrictMode case first passed under the forgetful-release mutant because the fake bridge kept its listeners in a Set and the router always passes the same function (the fake now wraps each registration, as preload's `onChannel` does); and the midnight case went red under the no-memo mutant only because the failing memo case left its bar, and a real midnight timer, mounted (each bar case now mounts and unmounts in `beforeEach` and `afterEach`).
