## 2026-11-27 -- Snap e2e D1 and C2 red on the beta.20 aggregate: Windows PowerShell's cold command lookup

Branch `fix/b20-snap-d1`, from the beta.20 aggregate at 7bf9a746.

What failed: the Snap e2e dispatch 46023467484 (e97cff73), D1 START (the
stand-in Claude Code never started on the tab's terminal within TAB_MS; the
terminal stayed blank) and C2 RECTANGLE run 1 (Codex showed no image
placeholder within 5 s of the paste, so the rule took the paste back). The
source between the last green dispatch (0ef650c4) and e97cff73 changed only
account naming. The beta.20 sign-in renewal is not involved: in every run the
stand-in recorded only its two `--version` calls and the tab's own launch,
never `auth status`.

### Cause (measured)

The first time Windows PowerShell 5.1 runs a cmdlet named bare, it looks
through every module on its module path for it. It puts
`Program Files\WindowsPowerShell\Modules` on that path ahead of its own folder
whatever it is given (read on the test machine). The GitHub Windows runner
holds 54 modules there (AWS, Microsoft Graph, SQL Server, among others), and
the tab's inherited path also starts with 103 Azure modules. With no module
analysis cache yet, as on the runner, that first look took 21.6 to 27.4 s
in diagnosis run 46040073797 (outside the app, 4 CPUs). A cmdlet named with its
module took 113 to 145 ms, and a call with no cmdlet 10 ms. On a faster runner
the start's calls took 8.4 s (46026344825).

Two things at start named a cmdlet bare: the owner-only script
(`New-Object`, `ConvertTo-Json`) that checks the scripts folders and the
home kept ready for the next new account, and the Claude Code tab's launch line
(`Set-Location`). So the cold start reached D1 two ways:

1. The app's own hold. A tab started at start on no account waited for the
   start's profile steps, and the steps waited for the ready home's
   owner-only check (round 1, measured in 46026344825 and 46028075097).
2. The tab's own launch line. Its Windows PowerShell began the line about
   1.1 s after it was written, and the line's `Set-Location` then waited for
   that PowerShell's own look. Each Windows PowerShell looks on its own. In
   46040073797, of two started 2 s apart, the second ended 2.3 to 2.6 s after
   the first, whether they shared a cache file or not. So round 1's reading
   in 46031920492 (the stand-in 7 ms after the start's calls ended) is not a
   wait of one PowerShell for another. It was not reproduced, and it is not
   explained.

### The forced condition, and D1 under it

Windows PowerShell 5.1 honours `PSModuleAnalysisCachePath`, read on the test
machine: it wrote the cache there about 13 s after the lookup, and left the
default cache alone. Diagnosis branch `diag/b20-snap-d2` (never merged) gave
each app a fresh, empty cache file. Each Windows PowerShell wrote a time,
with no command, at the head of its script or line and after its first
cmdlet. D1 ran in an app of its own per variant (run 46040073797):

- Fresh cache only, the runner's own modules:
  - With round 1's head (bare names), D1 was red. The start's calls never
    passed their first cmdlet; they were killed at 30.03 s and asked again.
    The tab's `Set-Location` had not returned 22.7 s after its line began.
  - With the module-qualified names, D1 was green: 2978 ms from the tab to
    the stand-in. The calls' first cmdlet returned in 250 ms, the calls took
    3.3 s, and the tab's folder change took 36 ms.
- Fresh cache plus generated modules in Program Files, as many as it took
  for the first bare lookup to take 44.5 s (12622):
  - The aggregate's order with bare names was red, held for the steps.
  - Round 1's order with bare names was red: the tab's folder change never
    returned.
  - The qualified launch line alone was green (6.5 s, held 5 s for the
    scripts folders, whose call was killed). A cmdlet-free folder change was
    also green (6.4 s).
  - Both qualified: green, 1.7 s. Both qualified with the aggregate's order:
    green, 1.8 s. The calls took about 1 s.

### Fix

The launch line changes folder with
`Microsoft.PowerShell.Management\Set-Location -LiteralPath`
(terminal-launch-line.ts `PS_SET_LOCATION`). The owner-only script names
`New-Object` and `ConvertTo-Json` with `Microsoft.PowerShell.Utility`. These
are the same cmdlets with the same arguments, loaded by module name with no
look. Round 1's start-order change stays: the ready home is checked after the
steps when they make no account. That decision now reads a listed primary
exactly as the first-run capture does. Unit test
`tests/unit/main/windows-powershell-module-qualified.test.ts` holds every
Windows route and the owner-only script to module-qualified cmdlets. It goes
red under a bare `Set-Location`, a bare `New-Object` or `ConvertTo-Json`, and
a wrong module. The Snap e2e now runs each app with a fresh, empty module
analysis cache, so every run meets the cold start. No timeout changed, and
nothing was re-run to get green.

### C2

It reproduced once under the forced condition with bare names (46040073797,
the Codex part's bare-names variant): C3 run 3 got no placeholder. Round 1's
log line said the composer held the whole path, 106 characters, as text. The
press's paste came 125 to 135 ms after the start's two owner-only calls were
killed at their 30 s limit and asked again, which starts two new cold
lookups. With qualified names, all six presses pasted and sent. The cause is
not proven: the timing is measured once, and why Codex took that paste as
text is not known. The fix takes away the condition it came with; it is not
shown to cure C2.
