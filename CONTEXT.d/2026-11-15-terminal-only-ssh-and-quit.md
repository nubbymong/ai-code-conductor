## 2026-11-15 -- A Terminal only SSH tab opens with no launch prompts, and quitting leaves it alone (2.1.3-beta.4, PR 6)

A Terminal only SSH config is a terminal. Two parts of the app still treated it as a session that might start Claude.

**Problem 1: the prompts.** With an "After connecting, run" command saved, the tab stopped at "Run post-connect command?" after login. Once the command had run, the app could not tell where it had landed and asked "Couldn't verify where that landed, launch anyway?". Nothing is ever launched in a Terminal only tab, so both questions had no good answer. A config whose command attaches to a tmux session on the host took two clicks to open, and the second one offered to start Claude inside that session.

**Change.** In the SSH flow of `src/main/pty-manager.ts`:
- A Terminal only tab types its post-connect command by itself, at the moment the offer used to appear: the first shell prompt after login, or, on a zsh host (whose `%` prompt the session's own pattern does not know), the pane going quiet for 1.5 seconds with that prompt as the last prompt read.
- When the command is done the tab goes straight to its terminal state (`shell-only`). There is no "Launch Claude" and no "launch anyway". The same holds when the config enters a container: once inside, the tab is the user's terminal, and leaving the container by hand raises nothing.
- The command is typed only at a shell prompt, and that is decided by the whole check the partner terminal's folder line already uses (`isPartnerShellPrompt` in `src/main/ssh-partner-folder.ts`): the prompt the last read ended in has a shell prompt's shape, and neither it nor the tab's recent output (the prompt's own line across reads, and the line above it) names a sign-in word (a password, a passphrase, a one-time code). So a sign-in prompt that two reads split, or one with its words on the line above a bare prompt, gets nothing. After a password the flow typed itself, a bare `> `, `$ ` or `# ` gets nothing either: it may be a second sign-in step.
- The check is made twice: when the flow decides, and again 200 ms later at the moment of typing, on everything read and typed since. If the tab is no longer at a shell prompt then (a sign-in prompt arrived after output that only ended like a prompt), nothing is typed and the offer appears. A Skip, a CLI screen or an ended connection inside those 200 ms also types nothing, even when the prompt is still valid and no key was typed, because the flow is no longer in its running state: the attempt is given up for the connection and the state that event set (skipped, for a Skip) is left as it is. The offer replaces only this attempt's own state.
- Once the user has typed into the tab, the command is not typed by itself on that connection: the offer appears. A zsh host waits 1.5 seconds at its prompt, and the echo of what the user typed there can read as a prompt. What is typed while a sign-in prompt is the last prompt read is that prompt's answer (a password typed by hand) and does not count, and neither do the terminal's own replies to the host.
- Anywhere the command is not typed (the silence after a sign-in banner, a prompt the app does not recognise) the "Run post-connect command" offer stays, as before, and one click runs it. A Skip is kept too: the command is not typed later behind the user's back.
- The post-connect phase has an end. A command that attaches to something busy never goes quiet and may never show a prompt the flow knows, so the tab used to stay in its "running" state for as long as the work lasted, and a connection that dropped hours later was reported as "Couldn't reach the host". Now the phase ends 15 seconds after the command is typed at the latest, and at once when a CLI screen shows in the tab. Either way the tab becomes a terminal (`shell-only`) by the same step the flow takes when the pane goes quiet, and from then on the flow types nothing into it, whatever it shows later. This holds for a container entry too: one still unanswered after 15 seconds leaves the tab a terminal, with no "entry failed" message for what happens after that.
- The saved sudo password answers only the command's own sudo. In a Terminal only tab it is typed only after the command itself has been typed and before the phase ends. It is not typed while a CLI screen is showing, like everything else the flow types by itself. A config that starts Claude keeps its saved-answer step exactly as it was on 2.1.3-beta.3: none of these conditions apply to it.
- `SshFlowOverlay` shows no "Running post-connect command" card for a Terminal only tab. A command that attaches to something busy never goes quiet, and the card would have sat over the terminal until the phase ended.

A container entry that fails within the phase still shows its message with Run again and Skip. A config that starts Claude keeps every prompt it had: it still offers its post-connect command and still asks before launching.

**Problem 2: quitting.** A normal quit typed Escape, Ctrl-C and `/exit` into every open terminal that the app had not wrapped in its own tmux session. That included Terminal only tabs, partner terminals and SSH tabs still waiting at their prompt. In a tab attached to a tmux session on the host, those keys went to whatever ran there and ended it.

**Change.** Each PTY now records whether the app itself started a CLI in it (`appStartedCli` on the session entry): true for a local session of an assistant, and for an SSH session from the moment the flow types the launch line. It is cleared again when the flow sees that CLI has ended and the tab is back at the shell (its "claude exited to shell" step). `gracefulExitPty` types the exit keys only into a terminal where it is set. Every other terminal is closed, which drops the connection and leaves whatever runs on the far side as a closed terminal leaves it. A tmux-persistent remote is detached as before, and the update-install path (`killAllPty`) is untouched.

**What it costs.**
- An SSH tab where the user pressed Skip and started Claude by hand is closed on quit, not sent `/exit`. The app did not start that CLI, so it does not type into it.
- The app sees an app-started CLI end only in the moment after launch (the pane back at a bare shell prompt). One the user ends later by hand (`/exit`, then something else started in the same tab) is not seen, and that tab still gets the exit keys on quit, as before this change. The same is true of a local session.
- A host whose shell prompt itself names a sign-in word (a host called `pin`, a user called `token`), or whose prompt ends in none of `$ # > ~ %` (a theme that ends in a glyph), keeps the one-click offer for its post-connect command, on every connection. So does a host whose prompt is a bare sigil when the flow typed a saved password, a connection where the user answered a question before the shell that is not a sign-in prompt (a first connection's host key question), and one where the user typed ahead. After that click the tab is a terminal with no further prompt.
- The sign-in check is a word list, as it is for the partner terminal. A prompt that ends like a shell's and names none of its words (a host menu such as "Select target host [1-3]> ", a code prompt in other words) is read as a shell prompt and the command is typed there.
- Output that ends like a shell prompt before login has finished (a sign-in banner read that ends in `#`) is still read as one. If the sign-in prompt follows within 200 ms, nothing is typed and the offer appears; the saved SSH password is then not typed either, and the user signs in by hand. If it follows later, the command has already been typed ahead of it.
- A connection that ends within 15 seconds of the command being typed, before the phase has ended, is still reported as a failed connection.

**Tests.** Stand-ins only, nothing is started and no host is reached.
- `tests/unit/main/pty-ssh-terminal-only.test.ts` (new): the command typed unasked at a recognised prompt and on a zsh host, typed once, no launch prompt afterwards, the container case; where it is typed (the sign-in, split prompt, bare prompt, banner, typed-ahead and Skip cases, and the two controls for a hand-typed password and the terminal's own replies); the end of the phase (the deadline, a CLI screen, nothing typed afterwards, a container entry, a connection that ends later); the saved sudo password answering only the command's own sudo, and a Claude config's saved-answer step unchanged (a CLI screen before or inside its 100 ms window does not stop it); a Skip or an ended connection inside the 200 ms window of a refused write kept; a Claude config's flow unchanged; and the SSH side of the quit rule, with a partner terminal, a tab showing a CLI screen and an app-started CLI that has ended.
- `tests/unit/main/pty-quit-exit-keys-local.test.ts` (new): a local Claude Code session and a local Codex session still get the exit keys, a terminal tab gets none.
- `tests/unit/renderer/ssh-flow-overlay.test.tsx`: no card for a Terminal only tab while the command runs, the card for a Claude config, and the offer and the failed-entry message still shown.

**Before merge.** `src/main/pty-manager.ts` is in the SSH statusline live-matrix radius. The matrix (`npm run test:live:ssh`, whole pack per host) was run on this branch and on the 2.1.3-beta.3 base side by side, and the two read the same. The tests that failed on this branch failed on the base too (a reattach on a host whose CLI was not signed in, and a password lane whose remote tmux server would not start), except one whose own setup step on the host (creating a tmux session over a plain ssh command) failed once and passed when run again. The results are in the PR. The review pass the SSH flow requires is deferred to the round before the next stable release, under the beta exception in AGENTS.md. The one-click offer remains on hosts whose prompt the app cannot read, and a Terminal only config that enters a container now enters without a click.
