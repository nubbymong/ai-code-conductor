## 2026-11-15 -- PR numbers check: the SSH radius, pty-manager.ts and its cap (2.1.3-beta.5, section C)

**Problem.** Two numbers that decide how much a pull request costs lived only in prose. The live SSH matrix is owed when a PR touches one of eight files (AGENTS.md, "SSH statusline changes need the live SSH matrix"), and nothing told the author or the reviewer whether it did. And ADR-030 capped `src/main/pty-manager.ts` at 8,128 lines, but #681 (terminal-only SSH tabs, merged after the ADR was written) had already taken it to 8,366, and nothing would have noticed a PR that grew it further. ADR-030's own SDLC table says "a check that prints these numbers on every PR is its own slice, after beta 4."

**Change.**

- `scripts/ci/pr-numbers.mjs` (zero dependencies, like `change-scope.mjs`) reads the PR's changed paths against its base (the merge commit's first parent, depth-2 checkout) and writes a table to the job summary: whether the PR touches the eight radius files (and which), the length of `src/main/pty-manager.ts` against the cap (and the change against the base), and "live SSH matrix: owed" or "live SSH matrix: not owed".
- It fails only when pty-manager.ts grows past the cap: over the cap, touched by the PR, and not shorter than on the base. A file that is already over the cap is not blamed on a PR that leaves it alone or shortens it. The `cap-override` label lets a growing PR pass, and the summary says so. A file that cannot be read fails; a deleted file (the remote deletion in ADR-030) is under any cap. Anything it cannot read for certain (the changed paths, the base) is treated as touched: the matrix is owed.
- The cap is `PTY_MANAGER_LINE_CAP = 8366`, today's length. It only goes down: when a PR shortens the file, the summary says to lower the constant to the new length.
- `ci.yml` gains an always-on job named `PR numbers`, ubuntu, one step. Its only condition is the event (`pull_request`), like `Desktop test gate`: it decides inside, so it can never leave a check waiting and may become a required check later. Labels come from the event, so adding or removing `cap-override` runs it again. The action is pinned by commit. The `Test (os)` jobs are not touched.
- ADR-030 is corrected: 8,128 becomes 8,366 in the Context list and in the SDLC table, with one sentence saying #681 raised it before the check existed.

**Tests.** `tests/unit/scripts/pr-numbers.test.ts`: the radius list equals the eight backtick paths of the AGENTS.md paragraph (extracted, not copied); the table over fixed path lists (a renderer-only PR, one line in `ssh-tmux.ts`, each radius file on its own, look-alike paths); the cap (grow, at the cap, shorter, label, already over, deleted, unreadable, fail closed); `main()` with a fake git and event file; the ADR carries 8,366 and mentions 8,128 once; the job always starts on a pull request with no step condition. Each new case was red under a mutant of the new code.

**Not in this change.** It is not a required check. It does not read the live matrix result, only says whether one is owed (the matrix needs real hosts). It does not read labels from the API, so a run started again by hand replays the labels of its first event; a label change starts a fresh run. AGENTS.md is not edited.
