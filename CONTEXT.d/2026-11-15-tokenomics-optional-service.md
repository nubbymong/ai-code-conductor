## 2026-11-15 -- Tokenomics as an optional service (2.1.3-beta.4, PR 4)

**Why.** The usage index always ran: its worker was forked at every start, whether or not the Tokenomics page was ever opened, and nothing could switch it off. The owner asked for it to be a service like any other: it can be opted out of altogether, switching it back on catches up on what it missed, a manual Rescan exists, an account can be left out of the figures, and the files its walks touch are counted so the cost can be shown and a wider walk is caught.

**What changed.**

- A switch in Settings, General, Tokenomics (`tokenomicsEnabled`). It is on unless the saved value is exactly false, so nothing changes for anyone who does not touch it. Off, there is no supervisor: no worker is forked and nothing that exists only for it runs (its pricing refresh, the registry reload listener, the following of the account sessions folders). The database and each file's stored progress are left as they are.
- The switch applies at once. Main re-reads the settings each time they are saved (`applyTokenomicsSettings`, called from the settings-saved hook in `src/main/index.ts`): off stops the worker and drops its listeners, on starts a new worker on the same database. Because the worker keeps how far it read each file in that database, a worker started later reads only what was written since. This is the catch-up, and it needed no new code in the worker.
- Saved settings that cannot be read are no answer. The service reads them with the checked read and follows the rule the provider switches already follow (`provider-accounts.ts` `readSettings`, `accounts-service` `savedPreference`): no settings file yet is a fresh install and reads as on; a file that is there but cannot be read or parsed changes nothing, so a running worker is not stopped, a stopped one is not started and the accounts left out stay left out; and with nothing read since the app came up it does not start until a later read gives an answer. The log says so once.
- Everything that reaches the supervisor copes with there being none. The IPC handlers answer "off" plainly (no figures, an empty list, a status with `off: true`) instead of failing. The pushes to the window are attached to each supervisor as it starts, so one started later is forwarded like the first. A session attribution is handed to the service (`noteTokenomicsSessionAccount`): with a supervisor it goes to the worker, and with none it is kept (the latest per session, 4096 at most) for the next one, so a Claude session that runs and ends while Tokenomics is off is still recorded to its account when the catch-up reads it. Keeping it costs one map entry and no disk work. It is kept in memory, so it reaches the catch-up when Tokenomics is switched on again in the same run of the app; after a restart that session's usage is counted but not recorded to an account.
- The Tokenomics page shows "Tokenomics is off" with a Turn on button while it is off, and asks main for nothing. It shows the same when main itself says it is off although the settings in the window say on, so the page never waits for an index that is not running; Turn on then saves the setting again and asks main what it says now. The GitHub Copilot billing card stays under the off panel: it is GitHub's figure, not the usage index's. A worker now pushes its status as it comes up, so a page that is open when the service is switched on shows what was recorded before at once, not after a whole pass. A page that is switched on and off again before main has answered its first question subscribes to nothing.
- Rescan on the page (after a confirm) puts every file's stored progress back to its start and reads each file again from its first byte. Nothing stored is deleted. A turn read again carries the key it was stored under, so it is stored once and the totals do not move; the figures can only fill in. Asking again while one is under way changes nothing, so a re-read is never started over; the Rescan is under way until its pass has read every file and settled the accounts, so an ask while the accounts are settled is the same Rescan too. No pass says it is done while a Rescan still waits for its own pass, so the page's "Rescanning" does not clear early; and when the supervisor has no worker left to run it (its restarts are used up, it is shutting down, or its worker is alive but could not open its database, which leaves it never ready and never started again) Rescan answers "not running" instead of yes and nothing is held; a worker being started, or one to come after a crash, is still held for. New IPC channel `tokenomics2:rescan`.
- Accounts can be left out of the figures (`tokenomicsExcludedAccounts`, a list of account keys). This is a filter at the query layer only: main adds the list to every query and the database leaves those accounts out of the totals, the charts, the sessions list, a session's detail and the Account filter. It saves no disk work. The walks have one projects root for every account, so an account left out is still read and recorded, and putting it back shows all of it. Settings says so, and says that usage recorded to no account (older history, sessions run outside the app) stays in the figures. The window reads the saved list as main reads it (`tokenomicsExcludedAccountsOf` in the settings store, held to main's `tkExcludedAccounts` by a test), so a saved value that is not a list of account keys leaves nothing out there either and breaks neither the page nor Settings. The page lets go of an Account filter on an account left out, as the list changes while it is open and before it asks for anything when it starts (an account left out while the page was closed or Tokenomics was off). A session detail kept from before is not shown when the page starts, and an open one is asked for again when the list changes, closing when main has none for it. Settings asks for the accounts again each time a pass completes, so on an index that was empty the accounts its first pass records become choices.
- The totals and charts go by the account each stored turn carries. A session row carries one account, its first, so a Claude session resumed under another account is read turn by turn for the list, its detail and the session counts too: it is listed while any of its turns is kept, with the figures of the kept turns, under its own account while that is kept (so with both of its accounts kept it reads exactly as it does with none left out), else under the account of its latest kept turn. The Account filter and the session counts go by that same account, the one the row is shown under, in the query before the list is cut into pages, so a page stays full and in order: with its first account left out and the other chosen, it is listed and counted there, and with its first chosen it is not. With none left out that is the session's own account and the query is as it was. A session is read that way only when the account it was last attributed to is not its first, so no other session's turns are read for it. Two cases are left as they are and are said in `tk-db.ts`, each pinned by a native case. First, such a session keeps the session's last time and last model even when its last turn is one of an account left out: the list is ordered, filtered and paged by them, so a row shown with another time would sit out of order and no longer match the cursor after it; only its figures and its account go by the kept turns. Second, a session that went to another account and then back to its first is treated in the list and the counts as its first account's as a whole (the index keeps a session's first and latest account, not each change), so with that account left out it is neither listed nor counted while the turns it spent under the other account stay in the totals, and the list is short by those turns; its detail goes by its turns.
- Each full pass counts what its two walks touched (folders listed, names those listings returned, transcripts found) and how many files it opened. The figures ride the pass's `index-complete` message and the supervisor keeps the last ones (`getLastWalkStats()`), for the Services panel to show. The depth limit of 12 is unchanged: the owner's decision is that it changes only if a measurement shows it helps.

**The guard against a wider walk.** `tests/unit/tokenomics/tokenomics-worker-changed-files.test.ts` builds a fixture tree with transcripts under three roots and decoys just outside them, runs the real worker over a file system wrapper that records every folder listed and every file opened, and fails if a folder outside the roots is listed, if anything but the fixture's eight transcripts is opened, or if the counts differ from the fixture's exact numbers. Two more cases there hold the other ways a walk can widen: a chain of folders thirteen deep under each root, where the transcript twelve down is read and the one thirteen down is never found; and a link inside each root (simulated, so no link is planted where the file runs), which is a name in its folder and is never followed. What main hands the worker is held in `tests/unit/tokenomics/tokenomics-optional-service.test.ts`: the two transcript folders, each exactly. Each was checked to fail under a change that widens: the projects walk started one folder higher, the depth limit raised at either walk, either root handed one folder higher, and either walk made to follow a link to a folder (each walk on its own). Real links are in the CI suite (`tests/unit/native/tokenomics-reindex-accounts.native.test.ts`).

**Tests.** Host-safe, on plain Node: the service (off and on at start, off and on while running, the listeners, the accounts left out, settings that cannot be read, the attributions kept while off and carried between supervisors, the roots handed to the worker), the handlers (the "off" answers, Rescan and its "not running" answer, the list added to each query, pushes for a later supervisor), the supervisor (Rescan held, sent and refused, refused for a worker that could not open its database, the walk figures, the status at ready), the worker (counts, the guards, catch-up, Rescan, Rescan during a pass and while a pass settles the accounts, and asked again while its own pass settles them), the page and the Settings section (main's own "off", the Copilot card while off, a start let go before main answers, a saved list that is not one, an Account filter on an account left out while the page was closed or off, a cached or open session detail, the accounts asked for again as a pass completes), and two source pins: the settings-saved hook calls `applyTokenomicsSettings` (`tests/unit/main/tokenomics-settings-wiring.test.ts`) and the attribution goes through the service. For the real database, in the CI native suite (`npm run test:unit:native`, the Test job on Windows, macOS and Linux, which picks up every `tests/unit/**/*.native.test.ts`): `tests/unit/native/tokenomics-excluded-accounts.native.test.ts` (the accounts left out, a session resumed under another account, and with the Account filter, its pages included, the seven-day figures and the unpriced models, the progress reset), the Rescan cases in `tests/unit/native/tokenomics-worker-ingest.native.test.ts` (at rest, and with a part-read rollout, asked in the middle of a pass and asked again while it runs), and the real-link case named above. The native suite needs Electron and is not run on the development machine: CI is where these cases run on the real database.

**Not in this change.** Token counts on the page and the measured cost on the Services row are the next PR. Leaving a machine out comes with remote sessions. Rows for files that no longer exist are still not pruned.
