## 2026-11-14 -- Usage index: read only the transcripts that changed (planning #302, #306)

**Problem.** The usage worker listed every folder under `~/.claude/projects` and every Codex sessions folder, and asked the size of every transcript in them, on each watcher event (after 0.75 s) and on a 5 s timer. No file was read twice (each has its size, time and offset kept in the index), so the cost was the walk itself. With 25 working sessions it kept the worker at about a fifth of a core.

**Change** (`src/main/tokenomics/tokenomics-worker.ts`; the mark each cursor keeps is also a column in `src/main/tokenomics/tk-db.ts`).

- A Claude transcript the watcher reports, written or newly made, goes into a set, and the next sweep reads only the files in that set. No folder is listed.
- The whole tree is still walked at start, on a re-index, on an event only a walk can answer (no file name, a name that is gone, a folder made or moved), on any event in a Codex sessions folder, when a named folder is first watched or cannot be watched (below), and every 5 minutes as the net for anything the watcher missed.
- A folder reported as changed starts nothing on Windows, and a file that is not a transcript starts nothing anywhere (review fix; the folder rule is for Windows only since review round 2). Windows reports the folder beside every write to a file in it: an append to `proj\a.jsonl` gives `change proj` and then `change proj\a.jsonl`, and a nested one gives `change proj\sid\subagents` and then the file. As first written the folder's event counted as one that names no transcript, so on Windows every write by any session still walked the whole tree and the change did nothing there. A write of any other file under the projects folder (a tool result, a memory file, a subagent's `.meta.json`) walked it too. Each reported name is now looked at with one lstat, never a listing, and nothing is walked inside the watcher's callback: on Windows a folder reported as `change` is left alone (the file in it reports its own event), a file that is not a transcript and a link are left alone on every platform (the walk skips them too), and an event that starts nothing no longer starts the 0.75 s pause again. A walk stays due for no file name (an empty one included), a name that is gone or cannot be looked at, a folder reported as `rename` (made, or moved in: what it holds may have been written before the watcher reached it), and anywhere but Windows a folder reported as `change`. That report was measured on Windows only. On macOS and Linux it is not known to come beside a file's own event, and on macOS a folder's event can be all the watcher says when it has dropped the events below that folder, so there it makes a walk due, as it did before the review fix.
- The transcripts a sweep looked at are asked their size by the 5 s timer, and read when the size moved, as if the watcher had reported them (review fix). On Windows a write through a handle that stays open raises no watcher event for the file until the handle closes: five writes 500 ms apart reported nothing, then one `change` at the close. The 5 s walk used to find those writes; with the walk every 5 minutes they were found up to 5 minutes late. Every transcript a sweep looks at is noted for the timer: one it read, a newly made empty one included (so a session that makes its transcript and then writes through the handle it kept is covered from its first line), and one it found as the index already has it (review round 3). A worker that starts, in an app started again or started again by the supervisor, finds most transcripts like that. As first written only a transcript that was read was noted, so after a start a session that wrote through the handle it kept was found only by the next 5 minute walk. At most 200 are kept: the ones modified last, by the time each had when a sweep last looked at it, and of two modified at the same time the one noted first is dropped first (review round 3). A walk over thousands of old transcripts therefore leaves the timer 200 to ask about, the ones being written among them wherever the walk finds them. As first written the 200 found last were kept, and a walk finds transcripts in the order the folders list them, so a first index could drop a transcript being written for an old one listed after it. A write through a handle that stays open moves the file's time as it is asked from outside (under "Measured"), so such a transcript counts as modified at its last write. None is dropped for its age (review round 2). As first written one was dropped 10 minutes after it was last read, and a session that paused for longer and then wrote through the handle it kept was found only by the next 5 minute walk: such a write reports the folder at most (under "Measured"), which names no file. No other reason for a time bound was found, since the 200 already bound the cost. One that could not be read is not asked about at every tick: it waits for its next report or the next walk. One whose size check fails is forgotten only when it is gone (`ENOENT`, or `ENOTDIR`); after any other failure (a file in use, a drive that does not answer) it is asked about again at the next tick (review round 2; any failure used to forget it, and its later writes then waited for the next walk). A transcript that 200 others modified later keep out of the list, and that is then written through an open handle, is found by the next 5 minute walk, and asked about from then.
- Whether Claude Code appends and closes, or holds a stream open, is not known. This repository holds no Claude Code source or documentation that says how a transcript is written, and no real CLI is run on the development machine, so it was not measured. The size check is needed either way: other writers (a sync tool, a future Claude Code) may hold a handle, and a missed watcher event is covered the same way.
- A full walk that leaves work behind runs again until every file is read. A file is read one budget per pass (16 MB of a Claude transcript, 64 MB of a Codex rollout), so a large first index or the one-off Codex account re-read takes many passes. As first written (PR #655) the next walk was then up to 5 minutes away, one budget of each file every 5 minutes. Now the next pass follows after the usual 0.75 s pause while every file left with bytes moved its cursor, so each pass reads further and the passes end when the bytes do. A pass that left bytes without moving a cursor (a short read) and a walk that failed part-way are retried by the 5 s timer, never at once. Once a walk has read everything, nothing walks again until a walk is due.
- Rollups left dirty with no walk due are rebuilt at the next 5 s tick, with no walk (review round 2). A walk that has read everything finishes the one-off Codex account re-read and rebuilds the daily and hourly rollups when they are dirty. They can still be dirty after it: a session attribution that arrives between two pages of the rebuild leaves them dirty for another one, a rebuild can fail, and an attribution the rollups cannot follow leaves them dirty at any time. The 5 s walk used to rebuild them again; with the walk every 5 minutes the totals by account and the hourly rollup stayed stale for up to 5 minutes. Now the changed-files sweep rebuilds them once it has read what was reported, and the 5 s timer starts that sweep for the rebuild alone when nothing was reported. The conditions are the walk's own: the app has named its account folders, and no walk is due (one is due while any file has bytes left to read, and it settles the accounts itself). Making a walk due instead was the other way to do it, and would have listed every folder to rebuild rollups that the reading of no file changes. The check is one read of one row of the index per tick.
- A changed-files sweep that fails part-way makes the next sweep a full walk, run by the 5 s timer and never at once. The reported files are taken out of the set as the sweep starts, so the ones it had not reached waited for their next report or for the next timed walk.
- A named folder with no watcher is tried again by the 5 s timer. A folder has none when it did not exist as the worker was told of it (`~/.claude/projects` or `~/.codex/sessions` on a new computer, a Codex account's sessions folder before its first session) or when its watcher failed. Before the changed-files sweep the 5 s walk found what was written there; with the walk every 5 minutes it would have been found up to 5 minutes late, for the rest of the run. Now a folder that does not exist costs one check per tick and no walk; once it exists it is watched and walked once, for what was written before its watcher started; and a folder that exists and cannot be watched is walked by the 5 s timer, as every folder was. The failure is logged once per folder.
- A reported transcript that is a link is left alone and starts no walk. The full walk skips links; the report was checked with stat, which follows one, and is now checked with lstat.
- The files that could not be read are kept by path. Every sweep used to start that count again, and a changed-files sweep visits only the reported files, so after any reported change the count read none and the Usage page's note about transcripts that could not be read came and went between full walks. A changed-files sweep now takes a file out only when it tries it again, and a full walk starts the list again.
- A file deleted and made again at the path of one already read is read from its first byte, whatever its size (review round 3). The index keeps how far each file was read and reads on from there, and only a file shorter than that was read again from the top. One made again as long or longer was read on from the old offset: its first lines were skipped, or the first of them read from its middle, and their usage was not counted (a Codex rollout's later turns were stored as the old session's). Each cursor now keeps a mark of what was read: a hash of the file's first bytes and of the bytes just before the offset, up to 256 of each, with where they are. The next read checks the mark before it reads on, and starts from the first byte when those bytes are no longer there. Both runs are needed. The first bytes say whose file it is: two Codex rollouts can hold the same turn lines and differ only in their header. The bytes before the offset say that reading can go on from exactly there: a file can start as the old one did and go on otherwise. The mark is the file's own bytes and nothing the file system says of it, so it tells the same on every platform. On Windows a file made again at once has the creation time of the one deleted and only its file id differs (under "Measured"); elsewhere a file id may be given again to the next file made, and Node documents that the creation time may hold the change time where the file system keeps none, which moves with every write (neither measured here). A file put back with the same bytes (a copy, a sync) is the same file, and is read on. Only the hash is stored, never the bytes: they are part of a conversation, and the index holds none of it. The lines of a file read again from the top are stored once: a transcript line is keyed by its message and request ids and a rollout's turn by its session and position, so a line the old file also had is not counted twice. The column (`readMark` in `tk_files`) is added to an existing database with no mark on any row; such a file is read on from its offset as before and marked then, and nothing is read again for the upgrade. A build from before this change names its own columns, so after a downgrade it reads and writes the same database and leaves the mark as it was. The mark says where its bytes end, so back on this build it is checked there, and a file that build read on in is still the same file. A check that cannot be read counts the file as not read (it is tried again at its next report or the next walk), and a mark that cannot be read once the lines are leaves the cursor with none.

**Cost.** Before: one full walk per watcher event and per 5 s tick, so at least 12 a minute and up to 80 a minute while sessions write. After, on every platform: a tick lists no folder. It asks the size of each transcript in the list of those the sweeps looked at (one lstat each, at most 200) and of no other file, and reads one row of the index to see whether the rollups are dirty. The list is not emptied by time, and since review round 3 the first walk fills it, so an idle app goes on asking about the 200 transcripts modified last (all of them where there are fewer) every 5 s. A watcher event costs one lstat of the name it gives. A reported transcript costs one more size check and the read of its new bytes. On Windows with 25 sessions writing: no walk and no listing in a tick; 200 size checks per tick once the projects folder holds 200 transcripts (the 25 being written and the 175 others modified last), fewer where it holds fewer; two lstats per append (Windows reports the folder and the file); and one size check and one read per reported transcript in each changed-files sweep. Timed on the development machine, on plain files in a temporary folder: 25 lstats take about 0.35 ms and 200 take 3 to 5 ms, so a tick with the list full costs about a thousandth of one core at most. Since review round 3 a read of a changed file also makes two marks, one checked before it reads on and one kept after: two reads of up to 256 bytes and a hash each, about 11 microseconds a mark and 21 a read, beside about 65 for the size check, open, read of one line and close of the same file. A file whose time changed with nothing to read is opened once for the check, where it was not opened before. A walk notes every transcript it finds: 1 to 2 microseconds each with the list full (11 ms for 5,000 transcripts, 56 ms for 50,000), once per walk. The walks left are the one every 5 minutes and the ones under "Not in this change". In the test tree 59 timer ticks in a row list and read nothing and ask only the size of the five transcripts read at start, and the 60th, at 5 minutes, walks once.

**Measured** (Windows 11, NTFS, Node 24, `fs.watch` with `recursive`, a probe on plain files in a temporary folder; not measured on macOS or Linux). An append: `change` of the folder, then `change` of the file. A new file: `rename` and `change` of the file, at times `change` of the folder too. A new folder: `rename` of the folder, and `change` of its parent. A file written as a temporary file and renamed: `rename` of the temporary name as it is made and again as it goes, so at least one report names a name that is gone, then `rename` of the final name. A delete: `rename` of a name that is gone. Writes through a handle that stays open: nothing for the file until the close, whether the handle was opened before the watcher started or after it. The folder was reported once (`change`): as a file in it was first opened for append, before any write, and not for later opens in that folder; an open for read and write reported nothing. A writer that opens its file and writes at once therefore shows as a first write that reports the folder and never the file, which is how the review saw it (round 2; this line used to say that nothing at all was reported until the close). Asking such a file's size from outside returns its true size, and makes Windows report the file at once (`change`); listing its folder does not. So a read found by the timer's size check is followed by a reported one, which finds nothing new or the bytes written since. Added with review round 3, same machine and Node: a write through a handle that stays open moves the file's time of last writing as `stat` and `lstat` give it from outside the handle (three writes 1.2 s apart, each showing its own time at the next check). A file deleted and made again at once at the same path has the creation time of the one deleted, to the nanosecond, and another file id.

**Not in this change.** Codex folder events are not narrowed: any of them still starts a full walk. A name that is gone still starts one, so a file under the projects folder that is deleted, or written as a temporary file and renamed, starts a walk each time. A folder made under the projects folder starts one (a new project, a session's first subagent). On macOS and Linux a folder reported as changed starts one, and how often those watchers report a folder was not measured. A transcript that grows by more than one budget between two sweeps still makes the next sweep a full one. The mark does not tell a file rewritten so that its first 256 bytes and the 256 before the old offset are as they were, nor one made again with the size and the time the index has (it is not looked at). A cursor written before the mark was kept is not checked until its file has been read once by this build. The 5 s timer asks the size alone, so a transcript made again with exactly the size the index has is read at its report (a delete and a make are both reported) or at the next walk. The rest of planning #306 is left alone: rows for files that no longer exist are not pruned, the root folder is not resolved to its real path, and there is no off switch.
