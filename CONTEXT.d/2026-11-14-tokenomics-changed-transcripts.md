## 2026-11-14 -- Usage index: read only the transcripts that changed (planning #302, #306)

**Problem.** The usage worker listed every folder under `~/.claude/projects` and every Codex sessions folder, and asked the size of every transcript in them, on each watcher event (after 0.75 s) and on a 5 s timer. No file was read twice (each has its size, time and offset kept in the index), so the cost was the walk itself. With 25 working sessions it kept the worker at about a fifth of a core.

**Change** (`src/main/tokenomics/tokenomics-worker.ts`).

- A Claude transcript the watcher reports, written or newly made, goes into a set, and the next sweep reads only the files in that set. No folder is listed.
- The whole tree is still walked at start, on a re-index, on an event only a walk can answer (no file name, a name that is gone, a folder made or moved), on any event in a Codex sessions folder, when a named folder is first watched or cannot be watched (below), and every 5 minutes as the net for anything the watcher missed.
- A folder reported as changed, and a file that is not a transcript, start nothing (review fix). Windows reports the folder beside every write to a file in it: an append to `proj\a.jsonl` gives `change proj` and then `change proj\a.jsonl`, and a nested one gives `change proj\sid\subagents` and then the file. As first written the folder's event counted as one that names no transcript, so on Windows every write by any session still walked the whole tree and the change did nothing there. A write of any other file under the projects folder (a tool result, a memory file, a subagent's `.meta.json`) walked it too. Each reported name is now looked at with one lstat, never a listing, and nothing is walked inside the watcher's callback: a folder reported as `change` is left alone (the file in it reports its own event), a file that is not a transcript and a link are left alone (the walk skips them too), and an event that starts nothing no longer starts the 0.75 s pause again. A walk stays due for no file name, a name that is gone or cannot be looked at, and a folder reported as `rename` (made, or moved in: what it holds may have been written before the watcher reached it).
- A transcript read in the last 10 minutes is asked its size by the 5 s timer, and read when the size moved, as if the watcher had reported it (review fix). On Windows a write through a handle that stays open raises no watcher event until the handle closes: five writes 500 ms apart reported nothing, then one `change` at the close. The 5 s walk used to find those writes; with the walk every 5 minutes they were found up to 5 minutes late. A transcript counts as read when a sweep finds it changed, a newly made empty one included, so a session that makes its transcript and then writes through the handle it kept is covered from its first line. At most 200 are kept, the ones read longest ago dropped, so a first index that reads thousands of old transcripts leaves the timer 200 to ask about for 10 minutes. One that could not be read is not asked about at every tick: it waits for its next report or the next walk. A transcript not read for 10 minutes and then written through an open handle is found by the next 5 minute walk, and asked about at every tick again from then.
- Whether Claude Code appends and closes, or holds a stream open, is not known. This repository holds no Claude Code source or documentation that says how a transcript is written, and no real CLI is run on the development machine, so it was not measured. The size check is needed either way: other writers (a sync tool, a future Claude Code) may hold a handle, and a missed watcher event is covered the same way.
- A full walk that leaves work behind runs again until every file is read. A file is read one budget per pass (16 MB of a Claude transcript, 64 MB of a Codex rollout), so a large first index or the one-off Codex account re-read takes many passes. As first written (PR #655) the next walk was then up to 5 minutes away, one budget of each file every 5 minutes. Now the next pass follows after the usual 0.75 s pause while every file left with bytes moved its cursor, so each pass reads further and the passes end when the bytes do. A pass that left bytes without moving a cursor (a short read) and a walk that failed part-way are retried by the 5 s timer, never at once. Once a walk has read everything, nothing walks again until a walk is due.
- A changed-files sweep that fails part-way makes the next sweep a full walk, run by the 5 s timer and never at once. The reported files are taken out of the set as the sweep starts, so the ones it had not reached waited for their next report or for the next timed walk.
- A named folder with no watcher is tried again by the 5 s timer. A folder has none when it did not exist as the worker was told of it (`~/.claude/projects` or `~/.codex/sessions` on a new computer, a Codex account's sessions folder before its first session) or when its watcher failed. Before the changed-files sweep the 5 s walk found what was written there; with the walk every 5 minutes it would have been found up to 5 minutes late, for the rest of the run. Now a folder that does not exist costs one check per tick and no walk; once it exists it is watched and walked once, for what was written before its watcher started; and a folder that exists and cannot be watched is walked by the 5 s timer, as every folder was. The failure is logged once per folder.
- A reported transcript that is a link is left alone and starts no walk. The full walk skips links; the report was checked with stat, which follows one, and is now checked with lstat.
- The files that could not be read are kept by path. Every sweep used to start that count again, and a changed-files sweep visits only the reported files, so after any reported change the count read none and the Usage page's note about transcripts that could not be read came and went between full walks. A changed-files sweep now takes a file out only when it tries it again, and a full walk starts the list again.

**Cost.** Before: one full walk per watcher event and per 5 s tick, so at least 12 a minute and up to 80 a minute while sessions write. After, on every platform: a tick lists no folder. It asks the size of each transcript read in the last 10 minutes (one lstat each, at most 200) and of no other file, and once nothing has been read for 10 minutes it asks nothing at all. A watcher event costs one lstat of the name it gives. A reported transcript costs one more size check and the read of its new bytes. On Windows with 25 sessions writing: no walk and no listing in a tick; about 25 size checks per tick (one per transcript being written, plus one per subagent transcript written in the last 10 minutes); two lstats per append (Windows reports the folder and the file); and one size check and one read per reported transcript in each changed-files sweep. The walks left are the one every 5 minutes and the ones under "Not in this change". In the test tree 59 timer ticks in a row list and read nothing and ask only the size of the five transcripts read at start, and the 60th, at 5 minutes, walks once.

**Measured** (Windows 11, NTFS, Node 24, `fs.watch` with `recursive`, a probe on plain files in a temporary folder; not measured on macOS or Linux). An append: `change` of the folder, then `change` of the file. A new file: `rename` and `change` of the file, at times `change` of the folder too. A new folder: `rename` of the folder, and `change` of its parent. A file written as a temporary file and renamed: `rename` of the temporary name as it is made and again as it goes, so at least one report names a name that is gone, then `rename` of the final name. A delete: `rename` of a name that is gone. Writes through a handle that stays open: nothing until the close. Asking such a file's size from outside returns its true size, and makes Windows report the file at once (`change`); listing its folder does not. So a read found by the timer's size check is followed by a reported one, which finds nothing new or the bytes written since.

**Not in this change.** Codex folder events are not narrowed: any of them still starts a full walk. A name that is gone still starts one, so a file under the projects folder that is deleted, or written as a temporary file and renamed, starts a walk each time. A folder made under the projects folder starts one (a new project, a session's first subagent). A transcript that grows by more than one budget between two sweeps still makes the next sweep a full one. The rest of planning #306 is left alone: rows for files that no longer exist are not pruned, the root folder is not resolved to its real path, and there is no off switch.

**Tests.** `tests/unit/tokenomics/tokenomics-worker-changed-files.test.ts`, the real worker on a plain Node run with an in-memory stand-in for the index database: only the reported transcript is read and no folder is listed; the full walk at start and on each kind of event that names no transcript, a Codex folder event included; nothing on the 5 s timer until the 5 minute walk; the repeat until drained for a Claude transcript and for a Codex account re-read, and that it then stops; no repeat at once after a short read or a failed walk, and the timer's retry; a changed-files sweep that fails, and the full walk at the next tick that reads what it left; a folder that does not exist at start (no walk until it does, then watched and read at the next tick) and a watcher that fails (walked every tick until it can be watched again, logged once); a reported link, simulated (lstat says link, stat and open follow it; no real link is planted, so the file can run on a developer machine); the count of transcripts that could not be read, across changed-files sweeps. The repeat cases, the failed-sweep cases, the two no-watcher cases, the link case and the count case failed before their fixes. Added with the review fixes: a write as Windows reports it, the folder and then the transcript, top level and nested (only that transcript is read, nothing is listed); a folder reported as changed with nothing else, and a file that is not a transcript, made or written (no sweep at all); an event that starts nothing does not put off a waiting sweep; a folder that was made, and each kind of event that still walks, with a check that the event itself lists nothing; a transcript written with no report (read at the next tick; one reported while still empty; a read renews its 10 minutes; not asked about after 10 minutes, and read by the timed walk; at most 200 asked about; a deleted one forgotten; one that cannot be read tried once; a size check that fails does not stop the timer). Run against the worker as it was before the review fixes, 13 of the file's 35 cases failed: the two Windows-shaped writes, the two no-sweep cases, the waiting sweep, the timer case (it now also counts the size checks), and every case of a transcript written with no report but the 10 minute bound. That bound and the events that still walk passed before, since nothing was asked about and every event walked; each was then checked to fail with its rule taken out of the worker (14 small changes to the worker, tried one at a time, each failing at least one case). `tests/unit/native/tokenomics-dirty-sweep.native.test.ts` (from PR #655) checks the totals against the real database in the CI native suite; it was not run on the development machine.
