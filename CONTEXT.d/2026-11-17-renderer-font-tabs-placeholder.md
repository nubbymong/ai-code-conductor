## 2026-11-17 -- Terminal font with GPU rendering, the Saved/Running tab row, the notifications placeholder (2.1.3-beta.7, C1)

Three renderer fixes in one PR (plan 2.1.3-beta.7, section C1).

**#313: GPU terminal text in a small sans font.** Bisected on the test VM (WINDOWS_1, session 0, the released 2.1.3-beta.6, GPU rendering on, a CDP probe of the live terminal's WebGL atlas). The cause is not the one the plan named first, and not the weight:

- The 2D canvas in Electron 44.11.3 ignores a `font` value that starts with whitespace and stays on its default, `10px sans-serif`. `' 450 13px "JetBrains Mono"'` is dropped; `'450 13px "JetBrains Mono"'` is kept. Every variant with a leading space was dropped, on a fresh canvas and on an OffscreenCanvas.
- `@xterm/addon-webgl` 0.19 builds each glyph's font as `${fontStyle} ${fontWeight} ${size}px ${family}`, and fontStyle is '' for upright text. So the whole atlas was drawn in 10px sans-serif, inside cells xterm had measured correctly with JetBrains Mono (7.8 px).
- A fresh atlas built after the font had loaded was still sans (load timing is not the cause). Weight 400 was still sans (the weight is not the cause). The same fresh atlas with the canvas font string trimmed drew JetBrains Mono.
- Electron moved from 44.5.1 to 44.11.3 on 2026-11-14 (#662), first shipped in 2.1.3-beta.1, which fits the first reports on 2026-11-16.

Fix: `terminal/canvasFontTrim.ts` wraps the 2D context `font` setters once, so the string reaches the browser with the CSS whitespace (space, tab, LF, CR, FF) at its ends removed; nothing else is touched, so no value a canvas accepted changes. It is renderer-wide: `main.tsx` installs it before React renders, so every canvas in the window (Excalidraw and pasted images too) behaves the same from the start, and `installWebglWithRecovery` repeats the call as a guard. xterm, the addon and the atlas are untouched, and the atlas is not rebuilt more often. It can go when the bundled Chromium accepts the leading space again, or the addon stops sending one.

The plan's font wait ships too, because the VM showed the race is real once the string is accepted: the face finished loading only 34 ms before the first glyph (a renderer reload). TerminalView waits for the regular and bold faces before its first initTerminal call (capped at 1.5 s, never rejects); the `document.fonts.ready` wait before the first fit and PTY start (unbounded before this PR) got the same cap. A face that is already loaded starts on the first frame as before. Within the cap the race is gone; a face slower than 1.5 s still leaves stand-in glyphs, because the atlas is never rebuilt for it. Both waits are cancelled when the view is torn down. `terminalFontOptions` is the one source for the family list, size and weights that xterm is given and the wait loads, and the family list no longer names the default font twice. No weight change (orchestrator default; the VM proved the weight is not the cause).

Proof on an unpacked build of 193b5e02 on the VM. That was the code head before the branch was rebased onto #700; its renderer code is the same as 410635d7 after the rebase (#700 changes only the session helper's Rust code and docs, and the commits after 410635d7 change only comments and docs). It was a cold start of the app process with GPU rendering on. Before any terminal existed, the trim was in place on both context kinds and a leading-space font read back trimmed. After the sessions resumed, two terminal views were mounted, and the one on screen (WebGL renderer) drew in JetBrains Mono, bold text included; the atlas pages are monospace. A renderer reload with a glyph logger showed the order: the regular and bold faces asked for while the face was loading, the face loaded, then the first cell measure (7.8 px), then the first glyph with its font accepted. Not done: a cold start after a VM reboot. The VM is shared with the track B idle measurements, and a reboot would bring up an autologon console session that was not there. The plan leaves the after-restart confirmation to the owner's PC.

**#315: Saved/Running tabs at UI scale 1.3 and the 200 px sidebar.** Each tab may shrink (min-w-0), its label truncates and carries its name as a title, the count badge never shrinks, and the row is a named query container (`@container/panel-tabs`). Below 13.75rem of row width the icon drops out and the tab's padding and gap tighten. Measured on the VM: "Running" is 2.99rem, the badge 0.75rem plus about 6 px a digit, the icon 13 px; the default 256 px sidebar at scale 1.0 gives a 14.9rem row, so the default look is unchanged. VM matrix on the same 193b5e02 build (scale 0.8, 1.0, 1.3 by width 200, 256, 420, both tabs): every tab has scrollWidth <= clientWidth and its badge inside the tab and the sidebar. Labels are whole everywhere except scale 1.3 at 200 px, where "Saved" is whole and "Running" shows 51 of its 62 px, so it reads "Run..." (11 px short). The sidebar minimum is unchanged.

**#314: the Hooks Gateway "Desktop notifications (coming soon)" checkbox** is gone, and the card no longer calls the gateway the foundation for upcoming notifications. It used no state of its own. app-knowledge, tips, the Feature Guide and README never mentioned it; the 1.3.x changelog lines stay as history. The three Codex lines of the card text are unchanged (WP1 manifest line count).
