## 2026-11-23 -- Snap on Windows takes its picture with the helper's capture mode and our own overlay; the new Snap is the default (beta.16 A1, aicc_planning#401)

- S8 steps 2 and 3 on Windows (ADR-030 D3, D4). A press of Snap, Rectangle runs the bundled helper's `capture --out <folder>` into a press folder under the user data folder (`snap-capture/press-*`, removed on every path), reads its one line, ends the child through its own handle after 2 s (P21's reading), reads each 32-bit bottom-up BMP, matches each to one of Electron's displays by physical bounds, opens A2's overlay (`openSnapOverlays`, src/main/snap/overlay.ts) and cuts the answer at the display's physical pixels; then today's 1920 cap and JPEG and today's delivery. The engine is `src/main/snap/engine.ts` (Electron-free, behind ports); `windows-engine.ts` connects it.
- Exit 3 (no desktop: an SSH session, a service, a locked screen or an elevation prompt) captures nothing. Every other failure (exit 1, 2 or 4, a start that fails, no answer in 2 s, a line or picture it cannot read, an unmatched display, an overlay that fails, named by the overlay's own reason) hands the press to the previous Snap. Each press logs one `[snap] new engine:` line: the outcome, the helper's time, each display's size and scale; never a path or a pixel.
- The choice is Settings, Custom Commands, Snap, "Snap on Windows: New / Previous" (`snapEngineWindows` in magic-buttons.json, saved only when the user picks). Nothing saved means the default, New (`SNAP_ENGINE_DEFAULT_WINDOWS`, src/shared/snap-engine.ts); a saved Previous is kept. macOS and Linux keep the previous Snap: the capture mode exits 4 there.
- `electron-screenshots` is no longer imported at main's start: the first press that uses the previous Snap loads it (`loadPreviousSnap`, screenshot-capture.ts). On macOS and Linux that is the first press; this was read on the Windows runner only. Measured on the runner before the change (snap-e2e run 45271463233): at start main held 36 files of the package and one native add-on (node-pty's conpty.node); after a press of the previous Snap, a second (node-screenshots), which the package itself loads at its first capture. So the add-on count at start does not change; the package's files move to the first press that needs them. Each press the previous Snap takes writes one line to app.log: `[snap] previous engine: loaded; it takes this press`, or, when its package cannot be loaded or started, `[snap] previous engine: its package could not be loaded (<error name> [code]); nothing captured` (never the error's message, which can hold a path). A press with Previous chosen is read by that line, on the runner (snap-e2e D8) and on the VM.
- snap-e2e (dispatch only, `snap_e2e`, windows-2025, `--retries=0`) drives the real button and overlay on the runner's desktop: a 200 by 120 DIP drag, Whole screen, Escape, the default, a forced failure, Previous chosen, the helper direct, and what main has loaded; it keeps a picture of the overlay mid-drag. Two causes found on the way, each from the run's own log: E2E_HEADLESS shows the app's window at -10000,-10000 (index.ts), so the spec puts it on the primary display; and the tab's program starts about 11 s after its Snap button shows (PowerShell's cold start on the runner, then the launch line), so D1 waits for the stand-in's ready line before any press types into it.
- The basic-user step (`runas /trustlevel:0x20000`, scripts/ci/snap-basic-user.mjs) read CAPTURES in 362 ms on the head (run 45273010875), but the runner's token kept a High mandatory level with the Administrators group for deny only, so it is not a reading from a session that is not elevated: the owner's first press is that reading.
- Owed: an ADR-009 pass before stable (aicc_planning #320 list): the helper child main starts and the files it writes, A2's window, preload and channels, and the test-only helper path. The overlay has not been opened in a packaged build; the VM line covers the packaged build from SSH (exit 3).
