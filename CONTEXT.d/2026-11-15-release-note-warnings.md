## 2026-11-15 -- Release notes can carry warnings, shown first

**Problem.** A release entry in `src/renderer/changelog.ts` had three change types (feature, fix, improvement) and one highlights line. There was no place for what a user should know before relying on a release: what changes for them, a known risk and what to do about it, how to go back. The 2.1.3 betas need one, because they start moving sessions onto a helper.

**What changed.**
- `ChangelogEntry` gains an optional `warnings` list of plain sentences. No entry has one yet: the release PR adds them.
- `scripts/gen-changelog.js` writes them first in the release's block, under a `### Warnings` heading, in `CHANGELOG.md` and in the GitHub release notes (`--notes`). A value that is not a list of strings is refused with the release named, and the refusal has an exit code of its own (3). The release workflow's notes step still falls back to a short release body when the generator fails for any other reason or has no entry for the version, and it now stops on that one code, so a release cannot go out with its warnings missing.
- `WhatsNewEntries` (the shared renderer behind the What's New dialog and the Feature Guide's release history) shows them first in the release, under its version line, in an amber block labelled Warnings. The release history lists every release, so each block has an id of its own, and the block is named by its visible label so a screen reader says the word once.
- `releaseWarnings` in `src/renderer/onboarding/upgrade-flow.ts` folds line breaks and drops blank items, the same way the generator does. It is not in `changelog.ts` because two existing tests replace that module with a list only.
- The generator now runs its command line only when started directly. Before, loading it from a test rewrote the real `CHANGELOG.md` as a side effect.
- The full-screen What's New summary a user meets after an update (`WhatsNewV2Step`) also shows warnings first, in an amber block ahead of its sections. That page is curated and does not print release notes, so without this an updating user would only find the warnings by opening the Feature Guide. It shows the warnings of the release that is now running and of every release the user passed over on the way to it, newest first, each under its version: someone who goes from one beta straight to the one after next never ran the beta in between. Passed over is told from the version whose notes the user last saw, which the upgrade flow already keeps and never lets run ahead of the last build that ran. It is not told from the summary's starting point: a tester's starting point is the last final release, so an earlier beta's warnings would come back on every later beta. A sentence that a newer release repeats is shown once. When the last version seen is not known, or the user went back a build, the running release's own warnings are shown. A fresh install sees none.
- When the summary has warnings, the run cannot be left before the summary was on screen. Skip on the page ahead of it, or leaving from a later page after jumping past it, lands on the summary once and leaves from there. With no warnings, leaving works as it did.
- `CONTRIBUTING.md` and the comments in `src/renderer/changelog.ts` now say how to write a warning: a plain sentence about a risk or a step the user must take, restated in each later release it still applies to.

**Checked.** With no warnings present `CHANGELOG.md` is byte for byte the same (`node scripts/gen-changelog.js`, then `git diff --exit-code CHANGELOG.md`), and the release notes of four existing versions are identical to the old generator's. The new tests are red on the old code: the generator ones with only the test exports added, and the load test with the direct-run guard taken out. The review fixes (the ids, the releases passed over, the leave rule, the exit code and the workflow line) were red before their source changes too, and the Feature Guide case now mounts the real page instead of reading its source.
