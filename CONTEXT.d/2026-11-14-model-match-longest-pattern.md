## 2026-11-14 -- Model matching: the most specific pattern wins (planning #309, item 4)

**Problem.** A model name that is no entry's id, alias or id-prefix is placed by pattern, and the first pattern to match in list order won. Each family's plain pattern (`opus`, `sonnet`, `haiku`) sits on the family's newest entry, which comes first. A partner platform puts its own text around a model's id (`us.anthropic.claude-opus-4-7-v1:0`, `vertex_ai/claude-opus-4-7@20260101`), so nothing but a pattern can place it, and every older Opus, Sonnet and Haiku was placed on the newest entry and took its label and price. The same day's model-data change fixed this for Fable only, by moving its plain pattern in the bundled file.

**Change.** `src/shared/model-registry.ts`, the pattern step of the matcher only. `resources/model-registry.json` is not changed (a copy of it is published on the model-data branch).

- The first pattern match in list order still decides which family the name is in, and whether it belongs to a shipped entry or to one the user or Sentinel added. So no name changes family, and an added entry takes no name from a shipped one.
- Within that family and origin, the entry whose pattern covers the most of the name now takes it: the longest pattern found in the name wins. `opus-4-7` (8 characters) beats `opus` (4).
- Tie-break: of entries whose patterns are the same length, the first in list order wins, which is the order the first match was taken in before (the bundled file's order when model data is in use).
- A pattern found only where the version number carries on after it does not count. `opus-5` is in `claude-opus-5-5` and in `claude-opus-5.5`, and names neither; without this, Opus 5.5 on a partner platform would have become Opus 5, because the newest entry carries only the plain pattern. A date (eight digits) is not a version, so `claude-opus-5-20260101` is still Opus 5. Such a pattern has still matched: it places the name when nothing covers more.
- A regular expression (possible only in a hand-edited overlay) has no length to compare. It ranks below every text pattern, and places a name when no text pattern does.

**What changes for a name, checked against the bundled file.** A one-off comparison (not kept as a test) placed 517 names under the old and the new rule: every id, alias and label, dated and bracketed forms, partner-platform and gateway forms of each Claude model, versions not listed, display names, names with two families in them, names of the other assistant. 91 changed. 90 are of one kind: an older listed model's own id, inside other text or written in capitals, now goes to that model instead of the newest. The other one is a second fix: a dated id of Fable 5 inside a platform's text (`us.anthropic.claude-fable-5-20260101-v1:0`) was placed on Fable 5.2, because `fable-5-2` is in `fable-5-2026...`; it is now Fable 5. No name changed family, no name became placed or unplaced, and no match changed kind (exact, alias, prefix, pattern). One more kind of name moves, which that list did not hold: a listed Fable version with a further version part after it (`claude-fable-5-1-9`, not a real name today) goes to the entry with the family's plain pattern, where the other families' such names already went.

**Kept.** Exact id, alias and longest id-prefix come first, unchanged. Every rule `src/main/model-registry-data.ts` holds a fetched model file to is as it was, and that file is not edited: a model only the fetched file has is still tried after every other entry, and a shipped model's patterns are still the bundled file's. `tests/unit/model-data-resolution-rule.test.ts` and `tests/unit/model-data-schema.test.ts` pass unchanged. A match by pattern is still reported as a pattern match, so the places that do not trust such a match for a label or an effort list behave as before.

**Not done here.** A dated id of Fable 5 with nothing around it (`claude-fable-5-20260101`) is placed by the id-prefix step, which is older than this change and not part of it, and that step still gives it to Fable 5.2 (`claude-fable-5-2` is the longest id it starts with). The usage index picks a price key the same way. That needs its own fix. A version written with a dot for an older model (`anthropic/claude-opus-4.7`) matches no version pattern and still goes to the newest entry.

**Tests.** New group in `tests/unit/model-registry-resolve.test.ts`: every Claude model in the bundled file in five partner-platform forms (older ones to their own entry, the newest still to the newest), the dotted and the dated cases above, and the rule itself on small lists (longest wins, tie-break in both list orders and with model data in use, a pattern held to the start, the version rule, a regular expression, the family and the origin limits, id-prefix first). 24 of the new cases failed before the change.
