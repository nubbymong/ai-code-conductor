## 2026-11-13 -- Windows: sessions restored at start find Claude Code without Check again

**What regressed.** Since PR #638 (first shipped in 2.1.1-beta.2) a launch on Windows names Claude Code by its full path or starts nothing; the bare `claude` the session's PowerShell used to resolve is gone on purpose. A tab restored at start was launched before the app's PATH had been brought up to date from the registry (that ran only before a check the user asked for) and before the PowerShell profile had answered, so it said "not found" until Check again.

**The fix.** At start, on Windows and with Claude Code switched on, main marks the start pending and walks PATH for Claude Code once, in a launch's order (`src/main/claude-start-lookup.ts`). The walk runs off main's own turn: a PATH folder on a share that does not answer can hold one file test for tens of seconds, and this is before the first window. Its answer is kept, so a launch soon after does not walk again.
- **Found** (the users who never had the bug): the start ends there. PATH is not refreshed, the registry is not read, and the version probe starts at once. A launch asked for during the walk waits for it, which is a few file tests in the usual case.
- **Not found:** main brings its PATH up to date from the registry once (the same `refreshWindowsPath`, same rules), then looks for Claude Code once (the PATH walk, then the PowerShell profile), then runs the version probe. A local Claude launch asked for meanwhile waits for them as a prepared spawn, then resolves as any launch does: a full path, or the same refusal as before.

**The two limits.** A launch waits at most `CLAUDE_START_LOOKUP_WAIT_MS` (15 s). That is a cap, not the sum of what the steps may take: the usual case ends well inside it, but each step has a longer limit of its own (the registry read, the profile question, the version probe and the first-start warm-up before it). Past the bound a launch resolves on what is known and is refused as before when that is nothing. It is also not a total for the launch: the hold comes after the launch's other waits at start (the scripts folders, the account profile steps), which this change does not touch. The start as a whole holds nothing after `CLAUDE_START_DEADLINE_MS` (30 s): when that passes while a step still runs, the start is no longer pending, every wait ends, one line is logged, and later launches do not wait at all. The steps themselves still run to their ends.

A refresh that added folders is counted once more when it ends, so a "not found" kept from a profile question asked while it ran is asked again.

**What else moves on Windows at start, with Claude Code switched on.**
- In the not-found case held launches are released once the version probe has answered, not before, so a tab the start releases does not report the version as not yet verified because it was held.
- Every launch asked for while the start is pending waits, each by its own bound, a retry of a refused tab too. The first wait the bound ends is logged once (`[start] Still looking for Claude Code after 15 s`), and so is a walk, a refresh, a lookup or a version probe that fails. A logger that throws ends no wait late and skips no step.
- The accounts service's look for each provider's CLI (what Settings, Accounts and the session dialog show) runs after the walk and, in the not-found case, after the refresh and the first lookup, not beside them, so it does not say "missing" until Check again for a CLI the refresh adds, and it asks the PowerShell profile nothing while the registry is read. It does not wait for the version probe, and its wait has the same 15 s bound, so no provider's status stays "not checked yet" for longer; past the bound it looks on the PATH there is, and that is logged.

**Unchanged.** No bare `claude`, no relative path, no new kind of PATH entry accepted. Everything off Windows behaves as before. So does a Windows start while Claude Code is switched off or its settings cannot be read: nothing is walked, held or refreshed, and the version probe is handed over at once. ADR-024 now names the read at start beside the checks the user asks for. Check again behaves as before with one difference: when its refresh ends having added folders, a PowerShell profile question asked while that refresh ran is asked once more, since its answer was for the PATH from before.

**How the wiring is tested.** What main does with the walk, the refresh, the lookup, the probe and the look for each provider's CLI is one function, `startClaudeAtBoot`, which index.ts hands the functions themselves; `tests/unit/main/claude-start-lookup.test.ts` runs it (pending before the call returns; the look for each CLI waits on the settled bound even when the accounts work had already ended). `tests/unit/main/pty-spawn-claude-start-lookup-bound.test.ts` puts the real start module behind the real `pty:spawn` handler. What is still pinned by the text of index.ts only: that main calls `startClaudeAtBoot` once, with those functions, after the launch rule is set and before `createWindow()`. Nothing runs index.ts in a test.

**Not measured.** No step was timed on a real Windows start; every figure above is a limit read from the code.
