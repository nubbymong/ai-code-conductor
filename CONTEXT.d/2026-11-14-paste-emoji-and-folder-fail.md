## 2026-11-14 -- A pasted emoji is no longer split, and one program file that cannot be read no longer hides its folder (planning #307 lead B12, planning #310)

Two small faults, one branch.

**Problem 1: a long paste.** A paste longer than 256 units is written to the terminal in chunks of 256 (`runChunkedWrite` in `src/main/pty-chunked-write.ts`). An emoji is two units of the string, a high one and then a low one, and each chunk is turned into bytes on its own. When the two fell on a chunk boundary, each half was sent alone and arrived as a broken mark.

**Change.** Once the end of a chunk is worked out, a chunk that would end on a high unit with its low unit next takes that low unit too. The chunk only ever grows, and by one unit, so a chunk size of 1 cannot stall. Plain text is chunked exactly as before, and its progress counts are the same. Half a character with no other half beside it is passed on as it came: a high unit followed by a letter, or a low unit with a letter before it, grows nothing.

Two things in the same file, found by the adversarial pass and fixed with it. A chunk size of 0 never advanced: it sent an empty chunk on every turn, for as long as the session lived (a negative size, or one that is not a number, did not send the data whole either). No caller passes one, and the size is now taken as a whole number of at least 1. And the comments said the chunk size and the progress counts were bytes. They are units of the string (what `data.length` counts), which is the same number only for ASCII; the comments say so now, and the two names in the progress hook's type say units. Nothing a caller sees is different.

**Who shares the helper.** Three callers, all in `src/main/pty-manager.ts`: a long write from the terminal (`writePty`, and the replay of writes held during a launch), a channel envelope (`pastePty`), and the tmux push over SSH. The tmux push sends Base64 and shell text only, so its chunks and its progress percentage do not change. A test now holds that: the push's command is plain ASCII, and the helper sends it in slices of exactly 256, its progress ending at the length of the command. That is a test only. `pty-manager.ts` and the SSH source files are not edited.

**Problem 2: finding a program on Windows.** The walks of PATH that find a program asked a folder nothing more once any file test in it had failed. One program file that cannot be read (access to it is denied, or it is in use while an update replaces it) was read as "this folder cannot be reached". So `claude.cmd` beside a `claude.exe` that could not be read was passed, and the launch ran a later folder's copy, or said Claude Code was not found.

**Change.** A walk still passes a folder, and asks it for no other name, when a file test in it fails: a share that is down is waited for once in a walk. The one exception is a short list of reasons known to be about the one file that was asked for, in a folder that did answer:
- `EPERM`: Windows says access is denied. That is the file's own permissions, or a file being deleted while another program still holds it open.
- `EACCES`: permission denied.
- `EBUSY`: the file is in use (another program holds it open and shares nothing, or has it locked).

Those pass that one file, and the file beside it is still asked for. The file that cannot be read is never named itself. Each of the three is an answer the folder gave, so asking it for the next name costs no further wait, even when the reason turns out to be the folder's (a folder whose every file is denied). The list is `ONE_FILE_UNREADABLE_CODES` in `src/main/windows-programs.ts`, read through `oneFileCannotBeRead`. It is applied in every place that makes the folder-wide decision, so they agree:
- `findOnWindowsPath` and `findOnWindowsPathAsync` (`src/main/windows-programs.ts`), which the launch, the checks and the lookups of the helper programs (git, gh, ssh, npm, node) go through;
- the Claude Code version probe's own file test (`statRegularFile` in `src/main/claude-cli-version.ts`);
- the Codex program lookup's own file test (`diskStat` in `src/main/providers/codex/spawn.ts`, which the lookup of node.exe for the resume list also uses);
- the resume list's own walk (`findOnPath` in `scripts/resume-picker.js`), which finds the Claude Code the list starts. It is a plain script that cannot import the app's walk, so it carries a copy of the list, and a test holds the copy to the app's list, code for code, and to the app's answer. Left as it was, the list would have started another Claude Code than the one the app's check found.

A file that is not there (`ENOENT`), or that is below something that is not a folder (`ENOTDIR`), is "no such file" in all four, as before.

**Why a short list (adversarial pass).** The first version of this branch went the other way: it passed only the one file for every reason outside the ten that say a folder cannot be reached (`FOLDER_UNREACHABLE_CODES`: the network, the host, a timeout). Windows reports some failures of a share that is down with no code Node.js knows (they arrive as `UNKNOWN`). Such a share, waited for once in a walk before, was then waited for once for each name: three times for Claude Code, and twice in the Codex lookup, which runs in place on the main thread with no time limit. Now every reason that is not on the short list passes the folder for the rest of the walk, exactly as before this branch: `UNKNOWN`, a read error (`EIO`), a broken link (`ELOOP`, `EINVAL`), a timeout, and an error with no code at all. `ENOTDIR` and `EISDIR` are not on the list either. The first says the folder itself is not a folder. The second is not what a file test answers for a folder (that is "not a file"), and on Windows it has stood for a drive that cannot do what was asked.

`FOLDER_UNREACHABLE_CODES` is still what one walk's file test hands on to a test that waited for another file in the same folder (#666). That rule, and the time limit of a walk (#658, #666), are not changed; `folderCannotBeReached` is private to `windows-programs.ts` again.

**What it costs.**
- A program file that cannot be read for a reason that is not on the list (a broken link, a read error) still hides the file beside it, as it always did.
- A file that cannot be read ranks exactly as a file that is not there, in every folder. In a walk that asks name by name (Claude Code: the launch, the version probe, the resume list) that changes the answer for a file in a LATER folder too. With PATH `C:\A;D:\B`, `claude.bat` alone in A, and in B a `claude.exe` that cannot be read beside a `claude.cmd`: the answer was `C:\A\claude.bat`, because the whole of B was passed, and is now `D:\B\claude.cmd`, which is the answer when B has no `claude.exe` at all. Kept on purpose, stated where the walk is described, and pinned in the tests of the walk, the version probe and the resume list.

**Tests.** Fakes only: the code under test asks for no file of the computer, and nothing is started. Eight files, 398 cases:
- `tests/unit/pty-chunked-write.test.ts`: the pair on a boundary is delivered whole, the bytes sent equal the bytes of the input, a chunk size of 1 does not stall, plain text and its progress counts are unchanged, a lone low unit after a boundary and a lone high unit before one grow nothing, and a chunk size below 1 still sends everything once.
- `tests/unit/ssh-tmux-push.test.ts`: the tmux push's command is plain ASCII and goes out in slices of exactly 256.
- `tests/unit/main/windows-programs.test.ts` and `tests/unit/main/windows-path-walk-deadline.test.ts`: a file that cannot be read next to a readable one is still found, in both walks and both orders, for each of the three reasons; a folder whose file test fails for any other reason is passed once, and a share that ends its test with `UNKNOWN` is waited for once, not once for each name; the later-folder case above.
- `tests/unit/main/windows-programs-own-file-test.test.ts` (new): the same through the walks' OWN file tests, with no stand-in passed in. The walk's other test files (the two above, and `tests/unit/main/claude-launch-walk.test.ts`) pass a stand-in: with an own file test that answered "not there" for every failure, or one that threw for a file that is not there, those three files stayed green and only this one failed.
- `tests/unit/main/claude-cli-version-locked-file.test.ts` (new) and `tests/unit/providers/codex/codex-binary-path-order.test.ts`: the same for the version probe and the Codex lookup, through their own file tests.
- `tests/unit/scripts/resume-picker-path-rule.test.ts`: the resume list's copy of the list is the app's list, and its walk gives the app's answer, reason by reason.

Run against the code as it was before this branch (97141019), 72 of the 398 fail; against the first version of this branch (9b2aaf2d), 64 fail. The cases that only pin what the branch already did were each run against a hand-made change that breaks what they pin, and failed. The stand-ins for "a folder that does not answer" in the older cases fail with a reason that says so (a timeout, a host that is down), where they used a plain error or one about a file.
