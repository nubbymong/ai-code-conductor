## 2026-11-14 -- A pasted emoji is no longer split, and one program file that cannot be read no longer hides its folder (planning #307 lead B12, planning #310)

Two small faults, one branch.

**Problem 1: a long paste.** A paste longer than 256 units is written to the terminal in chunks of 256 (`runChunkedWrite` in `src/main/pty-chunked-write.ts`). An emoji is two units of the string, a high one and then a low one, and each chunk is turned into bytes on its own. When the two fell on a chunk boundary, each half was sent alone and arrived as a broken mark.

**Change.** Once the end of a chunk is worked out, a chunk that would end on a high unit with its low unit next takes that low unit too. The chunk only ever grows, and by one unit, so a chunk size of 1 cannot stall. Plain text is chunked exactly as before, and its progress counts are the same. Half a character with no other half beside it is passed on as it came.

**Who shares the helper.** Three callers, all in `src/main/pty-manager.ts`: a long write from the terminal (`writePty`, and the replay of writes held during a launch), a channel envelope (`pastePty`), and the tmux push over SSH. The tmux push sends Base64 and shell text only, so its chunks and its progress percentage do not change. `pty-manager.ts` itself is not edited.

**Problem 2: finding a program on Windows.** The walks of PATH that find a program asked a folder nothing more once any file test in it had failed. One program file that cannot be read (access to it is denied, or it is in use while an update replaces it) was read as "this folder cannot be reached". So `claude.cmd` beside a `claude.exe` that could not be read was passed, and the launch ran a later folder's copy, or said Claude Code was not found.

**Change.** A folder is passed, and asked for no other name, only when the failure says the folder itself cannot be reached: the network, the host or the connection to it is down, or it did not answer in time. That is `folderCannotBeReached` in `src/main/windows-programs.ts`, the rule the shared file test of #666 already went by; it is now exported. Any other failure passes that one file, and the file beside it is still asked for. The file that cannot be read is never named itself. The rule is applied in every place that made the folder-wide decision, so they agree:
- `findOnWindowsPath` and `findOnWindowsPathAsync` (`src/main/windows-programs.ts`), which the launch, the checks and the lookups of the helper programs (git, gh, ssh, npm, node) go through;
- the Claude Code version probe's own file test (`statRegularFile` in `src/main/claude-cli-version.ts`);
- the Codex program lookup's own file test (`diskStat` in `src/main/providers/codex/spawn.ts`, which the lookup of node.exe for the resume list also uses);
- the resume list's own walk (`findOnPath` in `scripts/resume-picker.js`), which finds the Claude Code the list starts. It is a plain script that cannot import the app's walk, so it carries a copy of the rule, and a test holds the copy to the app's answer. Left as it was, the list would have started another Claude Code than the one the app's check found.

The time limit of a walk (#658, #666) is not changed.

**The cost.** Windows reports some failures of a share that is down with no code Node.js knows (they arrive as `UNKNOWN`), and those are not in the set. Such a folder was waited for once in a walk; it is now waited for once for each name the walk asks for (three for Claude Code). How long a launch waits for the walk as a whole is bounded as before, and the walk never names a later folder's program ahead of one that has not answered.

**Tests.** Fakes only: no file of the computer is read and nothing is started. `tests/unit/pty-chunked-write.test.ts` (the pair on a boundary is delivered whole, the bytes sent equal the bytes of the input, a chunk size of 1 does not stall, plain text and its progress counts are unchanged). `tests/unit/main/windows-programs.test.ts` and `tests/unit/main/windows-path-walk-deadline.test.ts` (a file that cannot be read next to a readable one is still found, in both walks and both orders; a folder that cannot be reached is still passed once, for each of the ten reasons). `tests/unit/main/claude-cli-version-locked-file.test.ts` (new) and `tests/unit/providers/codex/codex-binary-path-order.test.ts` hold the same for the version probe and the Codex lookup, through their own file tests. `tests/unit/scripts/resume-picker-path-rule.test.ts` holds the resume list's copy to the app's walk, reason by reason. 73 of the new cases failed before the change. The stand-ins for "a folder that does not answer" in the older cases now fail with a reason that says so (a timeout, a host that is down), where they used a plain error or one about a file.
