## 2026-11-17 -- Terminals that are not on screen take their output in batches (2.1.3-beta.7, plan section B3)

**What.** aicc_planning#303, renderer only. Every PTY chunk used to be written straight into its xterm, hidden or not. On the DOM renderer (every terminal but the active one) a write that scrolls refreshes the selection layer, and that redraw rebuilds the whole viewport through a path that ignores xterm's own pause for a hidden terminal. The ticket's profile put this (`handleSelectionChanged`) at 1.6 s per 90 s with 24 hidden terminals streaming.

- `src/renderer/components/terminal/hiddenOutputQueue.ts`: a terminal that is not on screen queues its output and writes it once a second (`HIDDEN_OUTPUT_FLUSH_MS`). The terminal on screen still writes each chunk at once, after anything queued.
- `TerminalView.tsx`: the per-chunk write path (the follow decision, the write, the repaint scheduling) is now `writeOutput`, called per chunk when visible and per batch when hidden. Byte counts, the resume nudge's timing and the output parse still see every chunk as it arrives. The queue is written at once when the tab is shown (before the atlas catch-up, WebGL and focus), before every line the app writes itself (the exit line, a spawn end notice, a launch failure), and before the resume nudge resizes the PTY. It is dropped with the terminal on unmount.
- "On screen" is the view's `isActive` prop: the active tab, on the sessions page, with no partner or other pane over it (App.tsx). The partner terminal has its own. So a terminal behind the canvas, logs or browser pane is batched too.
- Supersedes PR #653 (open since 2026-10-18, never merged), re-applied from beta with the additions below.

**Decisions.**
- A screen read is the one reader of a hidden terminal's buffer: the gate a Claude Code or Codex command, a canvas marker line or the Codex Plan mode `/plan` is typed behind (`screenRegistry`). #653 let it read a screen up to 1 s old, and an old screen can read "ready and empty" while Claude Code has already started a turn. xterm parses a write on a later task, so writing the queue just before the read cannot put it on that read's screen. The reader therefore writes the queue and answers "no screen" for that read when anything was queued; both gates read that as not at the prompt (fail closed) and read again. After any read the terminal writes each chunk at once for 3 s (`SCREEN_READ_LIVE_MS`), so the reads that follow (the marker loop reads every second, the Codex wait every 250 ms) see it as current as a visible terminal. Cost: a click on the status strip's Compact, model or effort control for a session whose terminal is covered by another pane, within a second of output, says "not at its prompt" once; the next click reads the current screen.
- The follow decision (sticky bottom, issue #73) is taken once per batch, on the viewport as it is before the batch: the user cannot scroll a hidden terminal, so the result is the same.
- No change to preload, IPC or main, so no adversarial pass; nothing in the SSH live-matrix radius (src/main untouched). SSH sessions share this output handler, so the desktop step includes one.

**Tests.**
- `tests/unit/renderer/hidden-output-queue.test.ts` (15 cases, fake timers): the queue itself.
- `tests/unit/renderer/terminalview-hidden-output.test.tsx` (13 cases): the real TerminalView mounted with xterm and IPC mocked (after terminalview-account-launch.test.tsx): the visible terminal, the batch and its single follow decision, shown again, hidden again, the exit line, a spawn end notice, a launch failure, the resume nudge on a restored session, a screen read, the unmount.
- Red before, run once against beta at be889cfa: the queue file failed to load (no module); the TerminalView file failed 9 of 13. The 4 that passed on beta guard what must not change: the visible terminal writes each chunk, and the spawn end and launch failure lines come after the output, and a terminal that was just read writes at once.
- Mutants, 17, each run once through the locked runner on the two files; every one of the 28 cases is red under at least one. Flush dropped on show; queue disposed instead of flushed before the exit line; visible terminal batched too; no flush before the resume nudge; dispose keeping its timer and queue; the view never disposing its queue; no flush before the spawn end line; no flush before the launch failure line; a screen read that neither writes nor answers no screen; one that writes but answers the old screen; no live window after a read; each queued piece written on its own; the timer re-armed by every chunk; a 2 s interval; an empty flush that still writes; a read that never, and one that always, says it was behind.
