## 2026-11-17 -- Terminals that are not on screen take their output in batches (2.1.3-beta.7, plan section B3)

**What.** aicc_planning#303, renderer only. Every PTY chunk used to be written straight into its xterm, hidden or not. On the DOM renderer (every terminal but the active one) a write that scrolls refreshes the selection layer, and that redraw rebuilds the whole viewport through a path that ignores xterm's own pause for a hidden terminal. The ticket's profile put this (`handleSelectionChanged`) at 1.6 s per 90 s with 24 hidden terminals streaming.

- `src/renderer/components/terminal/hiddenOutputQueue.ts`: a terminal that is not on screen queues its output and writes it once a second (`HIDDEN_OUTPUT_FLUSH_MS`). The terminal on screen still writes each chunk at once, after anything queued.
- `TerminalView.tsx`: the per-chunk write path (the follow decision, the write, the repaint scheduling) is now `writeOutput`, called per chunk when visible and per batch when hidden. Byte counts, the resume nudge's timing and the output parse still see every chunk as it arrives. The queue is written at once when the tab is shown (before the atlas catch-up, WebGL and focus), before every line the app writes itself (the exit line, a spawn end notice, a launch failure), and before the resume nudge resizes the PTY. It is dropped with the terminal on unmount.
- "On screen" is the view's `isActive` prop: the active tab, on the sessions page, with no partner or other pane over it (App.tsx). The partner terminal has its own. So a terminal behind the canvas, logs or browser pane is batched too.
- Supersedes PR #653 (open since 2026-10-18, never merged), re-applied from beta with the additions below.

**Decisions.**
- A screen read is the one reader of a hidden terminal's buffer: the gate a Claude Code or Codex command, a canvas marker line or the Codex Plan mode `/plan` is typed behind (`screenRegistry`). #653 let it read a screen up to 1 s old, and an old screen can read "ready and empty" while Claude Code has already started a turn. xterm parses a write on a later task, so a batch is on the screen only once xterm reports it parsed (the write's callback). The queue counts each batch it hands to xterm until that report; a read writes anything queued, and answers "no screen" while any batch is unparsed (one just written by the read, by the timer, or when the tab was shown). Both gates read "no screen" as not at the prompt (fail closed) and read again. After any read the terminal writes each chunk at once for 3 s (`SCREEN_READ_LIVE_MS`), so the reads that follow (the marker loop reads every second, the Codex wait every 250 ms) see it as current as a visible terminal. A chunk written at once (visible, or live after a read) is not waited for: that is how every terminal was read before this change, so the visible terminal's reads are unchanged. A batch whose write throws (xterm refusing data) is not waited for, so a screen can never stay unreadable. Cost: a click on the status strip's Compact, model or effort control for a session whose terminal is covered by another pane, within a second of output, says "not at its prompt" once; the next click reads the current screen.
- The screen-read handling past #653 came in two rounds: the first answered "no screen" only when something was still queued; Copilot's review of PR #708 pointed out a batch the timer had just written but xterm had not parsed, and the second round waits for xterm's parsed report.
- The follow decision (sticky bottom, issue #73) is taken once per batch, on the viewport as it is before the batch: the user cannot scroll a hidden terminal, so the result is the same.
- No change to preload, IPC or main, so no adversarial pass; nothing in the SSH live-matrix radius (src/main untouched). SSH sessions share this output handler, so the desktop step includes one.

**Measured on the test VM** (2026-11-17, B1's harness, one run each, shortened as B2's: N=25 only, 60 s idle settle, 60 s windows, 5 min busy settle, 90 s renderer profiles, no reduced-motion A/B/A, no ablations; motion settings the same in every run). Before: the installed 2.1.3-beta.6, harness at 7bf2fa5c, 09:45Z. Base: beta at be889cfa, built on the VM with `electron-builder --dir`, 09:16Z. After: this change's first commit 7bf2fa5c, built the same way, 09:29Z. The screen-read round came later and was not measured; it changes only screen reads, which the harness does not make. Figures at N=25 busy, before / base / after:
- Renderer CPU, % of one core: 24.60 / 23.89 / 23.31. Renderer main thread busy (CDP task time): 16.4 / 15.5 / 15.1 %. Style recalculations 40.8 / 41.2 / 40.9 per s; layouts 26.0 / 26.1 / 26.1 per s.
- 90 s renderer profile, inclusive ms: `_innerWrite` (xterm's write and parse loop) 253.8 / 264.2 / 59.1; `renderRows` 399.6 / 325.2 / 375.8; `createRow` 254.2 / 215.3 / 247.3; `handleSelectionChanged` 0 in all three; `writeOutput` 20.6 (after only).
- Reading: the write loop fell by about three quarters, from 264 to 59 ms against base: the hidden terminals' writes, now one per second each. Renderer CPU and main thread busy moved by less than the run-to-run spread B1 saw (1.3 to 2 points of renderer CPU; after is 0.58 below base and 1.29 below beta.6), so no CPU gain is claimed. `renderRows` and `createRow` (the DOM rows of the terminal on screen) differ by 74 ms between the two runs without this change, which covers the after figure.
- The plan's acceptance figures cannot be read on the VM: `handleSelectionChanged` is 0 in every profile, as in B1's runs (the fake CLI redraws its spinner in place and does not scroll, so the selection refresh the ticket profiled does not run), and style recalculations stay about 41 per second (the plan's figure of about 51 is from the owner's 2.1.2 profile). The owner's desktop step, with real Claude Code output, is the check for those.
- Idle at N=25: renderer 3.57 / 3.60 / 3.61 %. Microsoft Defender read 97.74 % of a core in the after run's idle window (0.85 and 0.96 in the other two, about 10 % busy in all three). Not investigated; that idle window carries the confounder.
