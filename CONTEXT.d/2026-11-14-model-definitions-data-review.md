## 2026-11-14 -- Model definitions as data: what the review round changed

The attack pass on the model-data change (same day, before any publish of the branch file) raised one major and five minor findings in the change. All six are fixed here, each with a test that failed first.

**An older file never overrides a newer build (major).** The fetched models win for an id both files have, and nothing ordered the two files. A last good copy kept by an earlier version, or a branch file that lagged behind a release, put back the earlier aliases, labels and prices (the `fable` picker row launching the previous Fable) with no log line. Each file now carries `"revision"`, the date of its last edit as a whole number (`20261114`). Model data whose revision is lower than the bundled file's is not used: a read is logged as not read with the two revisions, and an older last good copy is removed at start-up with one line. The same revision, or a later one, is used as before. The kept copy carries its revision. The ordering only holds if the revision is raised with every edit, so a unit test pins the bundled file's content beside its revision: an edit fails the test until the revision is raised and both are pinned again. `docs/versioning.md` has the release step (raise the revision, copy the file to the branch).

**The format is in the file's name.** The read is now `model-registry.v1.json` (built from `MODEL_DATA_FORMAT`). With one name and a strict shape, the first new field would have locked every installed 2.1.3 out of all later files. A later format is published beside this one, and the format 1 file is kept up for the versions that read it. The `formatVersion` line in the file stays as a second check.

**The file cannot empty a picker.** The earlier note said the file "can never take a model away"; it could still hide every model (`pickable: false`), drop every alias row and cut the effort levels to one. Now: whether a shipped model is offered is the bundled file's to say; alias rows and each assistant's effort levels join by name (the file adds and corrects, what only the bundled file has stays). A model the file adds may still be kept out of the picker.

**Less room inside the rules.** A price is at most 1000 per million tokens (was 100000). A model the build does not ship must have a full name: a Claude Code model `claude-<its family>-<a digit>...`, any other a name with a digit in it, so an entry named `claude` or `gpt` can no longer take the label and price of every model not listed yet. A pattern the bundled entry does not already have must be at least four characters. A redirect is followed only inside this repository's path on the host, not anywhere on the host.

**The overlay is the durable record.** A fetched file that carried a model Sentinel had added used to delete Sentinel's overlay entry for good; if the file later dropped the model, or the copy was lost, the model left the picker until a release. The overlay is now reconciled against the file shipped with the build alone (`getBundledRegistry`), so only a release retires an entry. The notice still closes at once. The cost: while both exist, the overlay entry is the one in use, as any overlay entry is.

**Partner-platform Fable ids.** Fable 5.2 held the plain `fable` pattern, first in the list, so `anthropic.claude-fable-5-1-v1:0` was read and priced as 5.2. Fable 5.2 now has the pattern `fable-5-2` and the aliases `fable` and `fable[1m]`; the plain `fable` pattern sits on the last Fable entry, so a display name ("Fable 5.2") or a Fable version not listed yet is still in the Fable family. Opus has the same weakness from before this change (the plain `opus` pattern is on its newest entry); it is not changed here.

**A fetched file never moves a name the build already places.** A shipped model's patterns are always the bundled file's (a fetched change to them is left out, not refused), and a name that is no entry's id or alias is tried against the shipped entries in the bundled file's order, and the user's own overlay entries, before a model only the fetched file has, so such a model is reached by its exact id or an alias and otherwise only by a name nothing else places (a dated form of a new model's id needs an alias in the file, and a partner platform's form of it stays with its family's shipped entry until a release); the picker order is still the file's (`tests/unit/model-data-resolution-rule.test.ts`).

**Still the owner's to do before the first publish.** Create the `model-data` branch with a ruleset (pushes by the owner only, no bypass for Actions, no force-push). Inside the rules a wrong edit can still mislabel a row or misprice a model; only who can write the branch protects that. Signing the file with the updater's key is a later option.
