## 2026-11-14 -- Windows: a launch no longer walks PATH on the main process's own thread (planning #309, item 7)

**Problem.** On Windows a launch names Claude Code by the full path found in a folder PATH names, or starts nothing, and it cannot wait. It reads the answer a walk off the event loop kept (the CLI check walks every 30 s and its answer is used for a minute). With no recent answer it walked PATH itself, in place, on the main process's own thread. A PATH folder on a share that does not answer can hold one file test for tens of seconds, and for that long no window repaints and no terminal gets its output. The start-up fix (2026-11-13) moved the start's own walk off that thread; the walk a launch makes at any later time was left as it was. The realistic case is a launch soon after the computer wakes: the kept answer is older than a minute and the share is not back yet. A launch that opens the resume list walked PATH the same way for node.exe.

**Change.**
- `src/main/windows-programs.ts`: `fileTestWithin`, a file test for the existing off-the-event-loop walk (`findOnWindowsPathAsync`, the walk the start uses; no second walker) that gives each folder a bounded time to answer, 2 s (`WINDOWS_PATH_FILE_TEST_WAIT_MS`). A folder that has not answered by then counts as holding no such program: the walk does not ask it again for another name and goes on to the next folder. An answer that comes late is not used. Never a guess.
- The file test left unanswered still runs to its own end on one of the few threads file tests share. While it runs, that folder is not asked again by any bounded walk (it is skipped at once), so a share that is down does not take one more thread, or one more 2 s, for every launch. It is asked again once the old test has ended.
- `src/main/claude-launch-walk.ts` (new): a local Claude launch with no recent answer to read waits for a walk of PATH made off the event loop with that file test, and reads the answer it kept. `pty:spawn` holds such a launch as a prepared spawn (`src/main/ipc/pty-handlers.ts`), the way it already holds one for the start, so a close or a newer spawn of the tab supersedes it. Launches asked for together wait for one walk. With a recent answer kept, the usual case, nothing is held and the launch goes straight on as before.
- A launch that opens the resume list also waits for the look for node.exe when no answer about it is kept. That look (`warmPickerNodeOnWindows`, which the CLI check runs too) now uses the bounded file test.
- `findClaudeOnWindows` (`src/main/providers/claude/spawn.ts`): when a walk of this PATH less than a minute ago found no Claude Code, and the PowerShell profile names none, that is the answer. It no longer walks PATH again in place. Before, a "not found" was walked again, in place, by every launch.
- After the start's own wait has run out with its walk still held (the last gap the start-up fix described: "the launch then walks for itself, in place"), the launch now makes this bounded walk instead.
- Review round: the three other callers of the same resolution wait for the same walk before they resolve. They are the path the Find Claude step shows (`IPC.CLI_PATH`, `src/main/ipc/cli-handlers.ts`), the first-run setup terminal (`setup:spawnCliSetup`, `src/main/ipc/setup-handlers.ts`) and the /insights terminal (`src/main/insights-runner.ts`). Without it, the change to `findClaudeOnWindows` above made them miss, for up to a minute, a Claude Code installed into a folder PATH already names: the Find Claude step could say "installed" (its check walks every time) and show no path, and the setup terminal refused to start. Now each makes the bounded walk off the event loop whenever no Claude Code is known for its PATH, so a fresh install is seen at once and none of them walks PATH in place. With an answer kept nothing is waited for.
- The setup terminal's wait can take seconds, so after it the handler asks again whether the terminal was closed (or asked for again) and whether Claude Code was switched off, before its warm-up starts anything.

**Kept.** No bare `claude`: a launch names a full path or is refused with the same message as before, and a folder that did not answer is never assumed to hold Claude Code. The order of the walk (claude.exe in any folder, then claude.cmd, then claude.bat), which folders are read, and the one-minute reuse are unchanged. Nothing changes off Windows. The start's walk, the CLI check's walk for Claude Code and the PowerShell profile question are untouched.

**The hold is on from main's start.** `startClaudeAtBoot` arms it, on every platform, because that is what main runs once at every start. A unit test that drives `pty:spawn` alone holds nothing and walks nothing, as before this change.

**What can still walk PATH in place.** These were not part of this item and are unchanged:
- The resolution's own last resort, for a caller with no walk of its PATH at all in the last minute. Every caller in the app now waits for a walk first, so this is left for a walk that failed and kept no answer, and for code that runs before main has started (unit tests that drive one handler alone).
- A session whose start is deferred inside the PTY manager for more than a minute (an account sign-in refresh), so that the answer its launch waited for has aged out.
- The walks for ssh.exe (an SSH session) and gsudo.exe (an elevated terminal).

**Not measured.** No real share was taken down. The 2 s bound and the behaviour of a file test on a dead share are read from the code and from the start-up fix's notes, not timed on a machine.

**Tests.** `tests/unit/main/windows-path-file-test-within.test.ts` (the bound: a test that never answers, the bound firing and not before, a late answer not used, the folder not asked again while held and asked again after, a normal folder not waited for, and the walk finding the program in the next folder). `tests/unit/main/claude-launch-walk.test.ts` (the launch reads the kept answer and walks nothing in place; with nothing found it is refused, never a bare name; one walk for several launches; the resume list's node.exe; armed at start; never off Windows). `tests/unit/main/pty-spawn-claude-start-lookup-bound.test.ts` gained cases with the real module behind the real `pty:spawn` handler (held as a prepared spawn until the bound, not held with a recent answer, superseded by a newer spawn, a terminal tab not held); those run on Windows only. Every file test in them is a stand-in. Review round: `tests/unit/main/claude-launch-walk-other-callers.test.ts` (new) runs the real Find Claude path handler and the real setup terminal handler over the real walk (a fresh install seen at once and agreeing with the check; nothing walked in place; a folder that does not answer given its bounded time; closed or switched off during the wait starts nothing; a second start waits for the same walk). The platform is a stand-in in them, so they are not limited to a Windows host; they were run on Windows. `tests/unit/insights-first-start.test.ts` gained one case: the /insights run waits for the walk before it resolves Claude Code.
