## 2026-11-14 -- Windows: a launch no longer walks PATH on the main process's own thread (planning #309, item 7)

**Problem.** On Windows a launch names Claude Code by the full path found in a folder PATH names, or starts nothing, and it cannot wait. It reads the answer a walk off the event loop kept (the CLI check walks every 30 s and its answer is used for a minute). With no recent answer it walked PATH itself, in place, on the main process's own thread. A PATH folder on a share that does not answer can hold one file test for tens of seconds, and for that long no window repaints and no terminal gets its output. The start-up fix (2026-11-13) moved the start's own walk off that thread; the walk a launch makes at any later time was left as it was. The realistic case is a launch soon after the computer wakes: the kept answer is older than a minute and the share is not back yet. A launch that opens the resume list walked PATH the same way for node.exe.

**The rule: PATH's order holds.** A walk may name a folder's program only when every folder before it has answered that it holds none (or that it cannot be reached, which a walk in place takes as none too). A folder that has not answered is never passed over. So what a launch names is what a walk in place would have named, or nothing.

**Change.**
- `src/main/claude-launch-walk.ts` (new): a local Claude launch with no recent answer to read waits for a walk of PATH made off the event loop, and reads the answer it kept. `pty:spawn` holds such a launch as a prepared spawn (`src/main/ipc/pty-handlers.ts`), the way it already holds one for the start, so a close or a newer spawn of the tab supersedes it. With a recent answer kept, the usual case, nothing is held and the launch goes straight on as before.
- One walk, shared (`src/main/claude-cli-probe.ts`, `sharedClaudeWalk`). The CLI check, the start, a launch and a headless run that ask about the same PATH value at the same time get the same walk. It asks the folders in PATH's order and waits for each answer, however long one takes. Its answer is kept when it ends, and only then.
- One deadline for the wait, not for a file test (`WINDOWS_PATH_WALK_WAIT_MS`, 20 s, `src/main/windows-programs.ts`). A launch waits for the walk until it ends or until 20 s after the walk began, whichever is first. The time is counted for the walk as a whole, and no file test has a time limit of its own. A launch that joins a walk already past its deadline does not wait again.
- Past the deadline the walk is inconclusive for that launch. No answer is kept, nothing already kept is replaced, and the launch is refused with a message of its own: a folder PATH names did not answer in time (`CLAUDE_PATH_NOT_ANSWERING`). It is not the not-found message, because nothing says Claude Code is missing. The launch does not fall back to a later folder's Claude Code, to the PowerShell profile's, to a walk in place, or to a bare name. The walk itself goes on; when the folder answers at last (a share that is down ends a file test by failing), the walk ends, keeps its answer, and the next launch reads it.
- The reason is the same whenever the walk under way is past its deadline, also when an earlier walk, under a minute ago, found no Claude Code. A launch with such a "none" kept is held for a new walk, to learn whether it still holds (a Claude Code installed since). When that walk has not said, the launch is told a folder did not answer, not that Claude Code was not found (round 3; before, it waited 20 s and was then told "not found").
- Why 20 s. A folder on this computer answers in well under a millisecond and a share that is up in a fraction of a second, so a walk still unanswered after 20 s is waiting on a folder that is down, not a slow one. A launch held for the start's own wait first (15 s) is still let go in about half a minute. The value bounds the wait only, and a value too short never names a wrong program. What it costs is refused launches: from the deadline until the walk ends, every launch with no answer to read is refused at once (no second walk is started), and the first launch after the walk has ended reads its answer. With a share whose file test takes about a minute or more to fail, that stretch comes round again. An answer is kept for a minute from the end of its walk, the CLI check starts the next walk 30 s after that end, and when that walk takes longer than the 30 s left, launches are refused from the moment the kept answer runs out until the walk ends.
- One file test at a time in a folder (`folderFileTest`, `src/main/windows-programs.ts`). A file test on a share that is down holds one of the few threads file tests share until it ends. So while a folder has a test outstanding, a walk that asks for the same file gets that test's answer, whatever it is, and a walk that asks for another file in that folder waits for it to end and then makes its own test. When the outstanding test ends, by an answer or by failing, the folder is asked again as usual.
- What a failed test hands to a test that waited for another file (round 3). Only a failure that says the folder itself cannot be reached: the network, the host or the connection is down, or it did not answer in time (`FOLDER_UNREACHABLE_CODES`: ETIMEDOUT, ENETDOWN, ENETUNREACH, ENONET, EHOSTDOWN, EHOSTUNREACH, ECONNREFUSED, ECONNRESET, ECONNABORTED, ENOTCONN). The test that waited is then not made, for one more such wait. Any other failure may be about the one file (access denied on it, a file in use, a broken link, a read error, an error with no code of its own), so the test that waited is made itself, as a walk in place would make it. Before, every failure was handed on: a node.exe that could not be read made the walk for Claude Code pass that folder and name a later folder's Claude Code, for a minute, for every launch.
- A walk waits behind another walk's test until its own deadline, and no longer (round 3). A test begun while a share was down can stay outstanding long after the share is back, and held every later walk of that folder for as long. Now the walk's deadline is given to its file tests: when it passes while a test still waits behind another walk's, the launch that waited is refused as above (the walk has no answer yet), and the walk makes its own test of that folder. The folder is asked, never passed over. At most two tests are outstanding in a folder at a time; with two, a walk waits for the one begun last. So one folder that is down holds one thread however many walks name it (the walk for Claude Code, the look for node.exe, a walk of another PATH value), and a second only once a walk has waited its whole deadline behind the first.
- A launch that opens the resume list also waits for the look for node.exe when no answer about it is kept, under the same deadline (`warmPickerNodeOnWindows`, which the CLI check runs too). That look keeps PATH's order the same way. Past its deadline the resume list is left out for that launch, the log says why, and Claude Code starts directly; a later folder's node.exe is never used and nothing is walked in place. The launch is held for this whenever it asks for the resume list, also when it names a conversation to resume (a restored tab asks for both, and a named conversation whose transcript is gone opens the list after all).
- `findClaudeOnWindows` (`src/main/providers/claude/spawn.ts`): when a walk of this PATH less than a minute ago found no Claude Code, and the PowerShell profile names none, that is the answer. It no longer walks PATH again in place. Before, a "not found" was walked again, in place, by every launch.
- The other callers of the same resolution wait for the same walk before they resolve: the path the Find Claude step shows (`IPC.CLI_PATH`, `src/main/ipc/cli-handlers.ts`), the first-run setup terminal (`setup:spawnCliSetup`, `src/main/ipc/setup-handlers.ts`) and the /insights terminal (`src/main/insights-runner.ts`). So a Claude Code installed a moment ago is seen at once, and none of them walks PATH in place. With an inconclusive walk the step shows no path and the two terminals are refused with the same message as a launch.
- The waits can take seconds. After it, the setup terminal asks again whether it was closed or asked for again, and both the setup terminal and the /insights run ask again whether Claude Code was switched off, before the warm-up that would start it.
- `pty:spawn` does the same (round 3). It asked whether the launch's provider is switched off once, before every wait, and a held launch can wait most of a minute (the scripts folders, the start's steps and its own wait, the walk). A launch that was held and is still wanted is asked about again after the last of those waits, and an Ask Conductor launch once more after its wait for the runs in the help folder. One that is refused then starts nothing, gives up its preparation and answers with the refusal, as at the top. A launch that was closed or superseded meanwhile answers that nothing started, as before, and is not asked about.
- PATH can be brought up to date while a launch waits, and a walk keeps its answer for the PATH it walked. When PATH reads differently once the walks have ended, the wait looks again at the PATH there is by then, off the event loop, up to three times in all.
- `pty:spawn` asks again whether there is a walk to wait for after its other waits (the scripts folders, the start's profile steps, the start's own wait), for any launch it held. An answer that was recent when the hold was decided can have run out meanwhile. The start's own wait and the launch's walk come one after the other.
- Deciding whether a launch is held reads only what is kept. It does not start the PowerShell profile question (the launch itself still starts it in the background, as before).

**Kept.** No bare `claude`: a launch names a full path or is refused. With Claude Code in no folder the message is the same as before. The order of the walk (claude.exe in any folder, then claude.cmd, then claude.bat), which folders are read, and the one-minute reuse are unchanged. Nothing changes off Windows. The PowerShell profile question is untouched: its kept answer is still one for the whole process, not for one PATH value.

**Changed for the CLI check and the start.** Their walk for Claude Code is now the shared one. They wait for it as long as it takes, as before; what is new is that they no longer start a walk of their own beside one already under way for the same PATH.

**The hold is on from main's start.** `startClaudeAtBoot` arms it, on every platform, because that is what main runs once at every start. A unit test that drives `pty:spawn` alone holds nothing and walks nothing, as before this change.

**What can still walk PATH in place.**
- The resolution's own last resort, for a caller with no walk of its PATH in the last minute and no walk past its deadline under way. Every caller in the app waits for a walk first, so this is left for a walk that failed and kept no answer, for the two gaps below, and for code that runs before main has started (unit tests that drive one handler alone).
- A launch whose kept answer runs out after `pty:spawn`'s last look: while an Ask Conductor launch waits (up to 5 s) for the runs in the help folder to end, or while a session's start is deferred inside the PTY manager (an account sign-in refresh). With a share that is down, the shared walk is normally past its deadline by then and the launch is refused instead of walking in place; the gap is the first 20 s of that walk.
- The walks for ssh.exe (an SSH session) and gsudo.exe (an elevated terminal).

**Not in this change.**
- Nothing is shown while a launch is held. The tab is blank for the wait (at most the 20 s above, after the start's own 15 s when the app has only just started). The deadline is the bound; telling the user what the app is waiting for is a UI change of its own.
- Several folders that are down are asked one after the other, one thread at a time. A launch may be refused until the walk has got past all of them, then it works.

**Known limits.**
- The 20 s count the time a file test waits for a free thread. The walk's deadline begins when the walk begins, not when its first file test runs, and only the walk for Claude Code and the look for node.exe keep to one test at a time in a folder. The app's other walks of PATH off the event loop (for git, gh, npm, the node tools check) make file tests of their own. With a share down and several of those under way, every thread file tests share can be held for as long as the share takes to fail, and a launch whose Claude Code is in a healthy folder is then refused, saying a folder did not answer, until a thread is free and the walk ends. Never a wrong program. Moving those walks onto the same rule is a change of its own.
- A walk waits for its OWN file test however long it takes. The bound above is for a test behind another walk's. So when the one walk of a PATH value has a test outstanding from before the share came back, launches on that PATH are refused until that test ends.
- A share that is down and fails with an error code outside the list above (Windows has reasons Node.js gives no code of their own) costs a test that waited there one more wait, one at a time. That side was chosen because the other side names a wrong program.

**Not measured.** No real share was taken down. How long a file test on a share that is down takes to fail, and so how often the walk ends inside the 20 s, is read from the code and from the start-up fix's notes, not timed on a machine. Which error code such a test fails with was not measured either: the list is made from what the codes mean. Every file test in the tests is a stand-in, so none of them runs against the threads real file tests share; the rule they pin is that no file test has a time limit of its own.
