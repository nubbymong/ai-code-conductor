## 2026-11-14 -- Fast beta cadence: the owner's process rules, and CI and the release made to match (ADR-028)

**Decision.** The owner set nine rules on 2026-11-13 and 2026-11-14 and approved them as the process simplification of 2.1.3-beta.1: the owner approves each beta's scope first; one review round per beta on a frozen head (one pass, one fix batch, one confirmation, then a narrow check of any later fix diff); majors and anything the beta introduces are fixed before the cut, minors in older nearby code become planning tickets; the beta release reuses green CI for the same tree; the version bump rides in the last content PR; CI runs only what a change touches, cancels superseded runs and does not restart tests on a label change; no new release-evidence gate; security paths keep the adversarial pass and the owner merges every PR; desktop testing is at release level on beta and pre-release on stable, not per PR. ADR-028 records them and amends ADR-009's interactive "fix -> re-attack until clean" and ADR-020's list of gates on a session PR.

**Written rules.** `AGENTS.md` has a new "Beta cadence" section and a "To cut a beta" line; `CONTRIBUTING.md` has "Beta cadence (maintainers)"; the adversarial-review skill's Phase 3 is now the one round, with a table in Phase 2 for what a round fixes and what becomes a ticket; `docs/agent-conventions.md` and `docs/versioning.md` say the same in their own places; ADR-009 and ADR-020 carry an "Amended by ADR-028" status line. For rule 9, CONTRIBUTING.md's "Desktop-test gate" section is rewritten, and the StartLoop and SessionLoop skills, `docs/loop-autonomy.md` and the PR body `scripts/loop-tree.mjs` writes no longer say a beta PR is merged "after a desktop test" or needs `desktop-tested`.

**ci.yml.** A `concurrency` block: the code events of one PR share a group that cancels; other label changes run in a second group per PR so they cannot cancel that PR's tests; a push to main and a dispatch get a group per run. The `test` and `codex-conformance` conditions run on a `labeled` event only when the label is `ci-run`, and never on `unlabeled`. The Test job reads the changed paths itself ("Decide the scope", `scripts/ci/change-scope.mjs`, checkout depth 2): a docs-only PR skips every later step on Windows and macOS and the job still ends green, because `Test (windows-2025)` and `Test (macos-latest)` are the required checks in all three rulesets and a job skipped as a whole never reports them. Linux keeps the whole suite. The job's last step is named `Tested tree <hash>`.

**Desktop test gate (rule 9).** The job keeps its name and still runs on every PR event. It runs `scripts/ci/desktop-gate.mjs`, which reads the pull request as it is now from GitHub (the event gives it the PR number only): on any base but `main` it prints one line (desktop testing happens on the released beta) and passes; on a PR into `main` it asks for one of the three labels, as the old script did; a PR that cannot be read fails the check. The workflow also starts on `edited` now, the only event a base change sends, so a green earned on a `beta` base does not survive a retarget to `main`; a text-only edit goes to the labels group and does not restart the tests, a base change is a code event. Read from GitHub on 2026-11-14: the three rulesets require `Test (windows-2025)` and `Test (macos-latest)` only, so the gate was a red X on PR #657, not a ruleset block.

**release.yml.** A new `ci-reuse` job (read-only, continue-on-error, never skipped) runs `scripts/ci/reuse-green-ci.mjs`; `build-windows` and `build-linux` need it and skip "Run tests" only when the channel is beta and it printed reuse=true. The script wants a green ci.yml run of this repository, not from a fork, on a PR or a push, for a commit whose tree equals the release commit's, with all three Test jobs green and each ending in a green `Tested tree <that hash>` step. Any doubt or API error is the full suite. Stable is unchanged; no signing, notarization, upload or publish step was touched.

**Why two conditions for the reuse.** The commit's tree is GitHub's own record, so the ci.yml that ran is the one in the released tree. The step is the job's record of what it checked out: a PR run tests the merge into its base, so a branch behind `beta` tested another tree, and a docs-only run tested nothing on Windows and macOS. Either way the step is absent or names another tree.

**Left as it was, on purpose.** `Changelog in sync` and the SSH smoke run again on a label change or a PR edit (about a minute together): a job skipped by its condition reports as passed, which would sit over an earlier red result for the same commit. The Codex conformance matrix is not path-scoped (about a minute per job).

**Tests.** `tests/unit/scripts/ci-cadence.test.ts` parses both workflows and evaluates their conditions against the events GitHub sends, with a small expression evaluator (`tests/helpers/gha-expr.ts`); `reuse-green-ci.test.ts` and `change-scope.test.ts` cover the two scripts with GitHub and git injected. The mutation journal for the scripts and both workflows is in the PR notes.

**WP1.** The new `ci-cadence` test names the `codex-conformance` job, so the legacy-Codex ledger moved: one new `added` row for the test, a note on the `ci.yml` row (only the job's start condition changed), the ledger re-skeletoned and `docs/wp1/legacy-codex-manifest.json` rewritten. The candidate check passes.

**Review round (one pass, this fix batch).** Eight minor findings, all from this change, fixed in one batch. (1) The reuse lookup accepted a pull-request run into any base; a PR run executes the workflow of the merge into its base, so the same tree did not pin the ci.yml that ran. It now counts only when every pull request GitHub lists for the commit is into `beta` or `main` in this repository and one has the commit as its head (`release/*` is left out: such a branch can be created with any ci.yml by anyone who can push). Checked against the live API: a merged PR's run has an empty `pull_requests` list, so the base is read from the commit's pull requests instead, which lists merged and open PRs but not one closed unmerged. (2) and (3) A run started again by hand replays its first event: the gate now decides from the live PR, and a re-run gets a concurrency group of its own so it cannot cancel the run on the newest commit. (4) Label and edit runs end green on the same commit and used up the lookup's ten job reads; they are now passed over (40 lists in all) and counted in the summary. (5) `docs/versioning.md` and `.github/copilot-instructions.md` still sent a maintainer to the bumping release script. (6) ADR-009's status line now covers the unattended cap. (7) and (8) Rule 2 says what the one round is off the security paths (owner to confirm the sentence) and defines "frozen head" and "narrow check" where the rule is.

**Follow-ups.** The first PR run and the first beta release run are the real proof (the PR notes say what each should show). The four slow PowerShell test files on Windows were not touched. The confirmation of the fix batch is owed by the orchestrating session (the beta's one round); `release.yml` is on the adversarial-review path table for its signing steps, which this change does not touch.
