## 2026-11-15 -- Account and session fixes for 2.1.3-beta.5 (planning #307: B2, B3, B4, B13, B14, B16)

One branch, six small fixes from the #307 lead list. None is in the SSH launch path, so no live SSH matrix is owed.

### A Mac session on a Claude account other than the primary one is refused (B3)

**Problem.** On macOS the Claude CLI finds its login through `$HOME`, and the app leaves `HOME` at the real home there (the profile homes mirror dot-entries only, never `~/Library`). A session started on a profile other than the primary one therefore ran as the Mac's own sign-in under the other account's name. Only the reviewer path refused it (`profileReviewRefusal`).

**Change.** `withProfileHome` (`src/main/account-profiles.ts`) refuses the launch first thing, before anything is composed, when the platform is macOS and the profile its home belongs to is not the primary one. The rule is shared with the reviewer's through one private function (`macNotPrimary`) and the platform is an argument (`profileLaunchRefusal`, and a fourth argument of `withProfileHome`), so it tests on any OS. The refusal is thrown with the managed-launch marker, so the existing deferred-spawn failure line writes it into the tab. The sentence is worded for every caller (a tab, a cloud agent, an Insights run), not for a tab only: "On a Mac, only your normal Claude sign-in can be used, so this account cannot start it. Choose your primary account and try again."

When the app cannot tell which account is the primary one (profiles.json unreadable, or no primary recorded) the launch is refused with its own sentence rather than let through. A home that is not under the profiles root has no account to judge and is left alone.

**Where the refusal shows.** The log marker in front of a refusal is for the log; `launchRefusalText` (`src/main/launch-refusal.ts`, no imports, so `claude-headless` can use it too) strips it and capitalises the sentence wherever a user reads one.

- Cloud agents: `dispatchAgent` answers a managed-launch refusal as `{ rejected: <sentence> }`, which the Cloud Agents page already shows as its banner. Before, the refusal was thrown, the page only logged it and Run did nothing; the project-settings refusal had the same hole and is answered the same way now. A retry goes through the same call. No agent record is made.
- Insights: a run's `error` carries the sentence, without the marker (the run fails visibly, as before). A cross-account member's error reads the same.
- Headless runs (the KPI extraction, Sentinel): the refusal comes back as `{ code: 1 }` with the sentence on stderr, as before, without the marker.
- Sign-in check (`readClaudeCliAuth`): on a Mac another account is an expected state, not a fault. It answers `{ authenticated: false, notChecked: "On a Mac, only your normal Claude sign-in can be checked here, so this account is not checked." }` before any wait or any run, so no "isolation fault" line is logged on every poll, and the Accounts panel shows the account as not checked rather than signed out (the credential file says nothing on a Mac, where the sign-in is in the keychain).
- Sign-out: on a Mac, another account's sign-out is refused up front with its own reason (`mac-not-primary`, "On a Mac, only your normal Claude sign-in can be signed out here, so this account was not signed out."), before the user is asked to confirm a sign-out that cannot happen. It used to read "could not prepare this account's Claude Code environment".

**Decision recorded: a plain terminal tab pinned to another account on a Mac is refused too.** `withProfileHome` does not know whether the launch is a session or a shell, and a shell in that account's home would carry the same mirrored dot-entries and the same keychain. If the owner wants a plain terminal to open there, the check would be skipped for `shellOnly` launches; that is a separate change.

### An account switched off never launches, wherever its id arrives (B4)

**Problem.** Only the account picker hid an inactive account. The main process resolved any id whose folder existed (`pty-manager.ts`, the local launch), so a restored tab or a saved session that named an account switched off since still started on it.

**Change.** `inactiveAccountRefusal` (`account-profiles.ts`) reads the saved list and answers a sentence when the account is there and switched off (the primary account is always active, as `isAccountActive` says): "The Claude account "<name>" is switched off, so nothing was started on it. Choose another account (for a tab, use Switch Account in its right-click menu), or switch "<name>" back on in Settings, Accounts." The wording fits a tab, an agent and an Insights run alike. `assertAccountActive(profileId, sessionId)` logs and throws it; the local Claude launch in `pty-manager.ts` makes that one call (one added line, `if (!shellOnly) assertAccountActive(wantProfileId, sessionId)`, with the import swapped), as soon as the id resolves and before the refresh wait and the project-settings check. A plain terminal tab names no session and is not refused. An account that is not in the list keeps the missing-account sentence. The check sits in the local region, outside the SSH branch.

**Every other launch of Claude on an account asks too.** Cloud agent dispatch and retry (`resolveAgentEnv`, answered as `rejected`, so a retry of an agent whose account was switched off since shows the sentence), an Insights run (`runInsights`: the run fails with the sentence on it), and Sentinel's Claude analysis (`analysisHome`: the run is refused with the sentence, which the panel shows). A version check starts no work on an account and is not refused.

**The launch picker no longer offers a switched-off account, not even a session's own.** `AccountLaunchGate` listed the session's pinned account even when it was switched off ("so a session can relaunch"), which under this rule always ended in the refusal. It is now not listed; a restored session pinned to one shows "The account this session last ran on is switched off. Choose another to start it." and the dropdown falls back to the primary account.

### A Codex session in a symlinked folder gets its status line and usage (B2)

**Problem.** The claim of a new Codex rollout compared the folder the rollout records with the folder the session was started in as plain strings (`telemetry.ts`). A session started in a symlinked folder has the link's name, while the rollout can record the real folder, so no rollout was ever claimed and the Codex tab stayed empty.

**Change.** The exact spelling is still tried first. A second look compares the two by real path (`sameFolderByRealPath` in `rollout-lookup.ts`, case-folded on Windows as the existing directory compare is), at the claim and at the rival check, so two launches in one real folder still contest one rollout. A folder that cannot be resolved never matches. Whether Codex records the real or the link path is not known; the rule accepts either. The real-path call is synchronous on the main thread, so the second look is bounded: only two absolute local paths are resolved (a relative spelling, and a UNC path written with backslashes or `//server/share`, are never looked at, since a share that does not answer can hold the call for its timeout), and each folder is resolved once per watch (the session's own folder once, however many rollouts are looked at; a failure is kept too). A mapped network drive that has a drive letter cannot be told apart by its spelling and is still resolved.

### Git and npm config kept elsewhere is seen in managed sessions (B14)

**Problem.** Every managed launch pinned `GIT_CONFIG_GLOBAL` to `~/.gitconfig`. Git ignores its XDG file (`$XDG_CONFIG_HOME/git/config`, `~/.config/git/config`) whenever that variable is set, so a config kept only there was invisible in a managed session.

**Change.** `sharedConfigPins` (`account-profiles.ts`) pins `GIT_CONFIG_GLOBAL` only when `~/.gitconfig` exists and no XDG git config does; with neither, only the XDG one, or both, the variable is left alone and git reads what a normal terminal reads. `npm_config_userconfig` is pinned only when `~/.npmrc` exists. A pure function over an existence check, tested with a temp home. Where both git files exist, git now reads both, as in a normal terminal, which differs from the old single-file rule. The old pin was belt-and-suspenders against a hard-linked profile-home copy of `.gitconfig` drifting from the real one; for a user who has both files that guard is gone, and git reads the profile home's mirror of `.gitconfig` plus the XDG file. Keeping the pin when both exist and pointing `GIT_CONFIG_GLOBAL` at the XDG file only when `~/.gitconfig` is absent would keep it; that is a design choice and was not made silently. One layout is handled further: the profile-home mirror skips a symlink at the root of the real home, so with a symlinked `~/.gitconfig` and an XDG git config the profile home has no `.gitconfig`. In that case only, `sharedConfigPins` adds `GIT_CONFIG_COUNT`, `GIT_CONFIG_KEY_n` and `GIT_CONFIG_VALUE_n` entries (an `include.path` of the real `~/.gitconfig`), continuing any count already in the environment and leaving an unreadable count alone. Git then reads both files and `GIT_CONFIG_GLOBAL` stays unset. A regular `~/.gitconfig` gets no include, because the mirror hard-links it and an include would read it twice.

### Elevated shells on macOS and Linux keep the protective variables (B13)

**Problem.** An elevated terminal tab starts through `sudo`, whose default `env_reset` drops `CLAUDE_CODE_DISABLE_MOUSE` and its siblings, so a hand-run `claude` inside it took the mouse again.

**Change.** The tab now runs `sudo env NAME=value ... <shell> -l` (`elevatedKeptVariables` in `providers/claude/spawn.ts`) for the four non-secret protective variables, only those that are set and only plain values. No secret value is on the command line, where `ps` shows it; a secret command in an elevated tab still expands empty, as before. When the user opted out of all four the command is the old `sudo <shell> -l`. Windows (gsudo) is unchanged.

### Known issue: no tmux copy for 32-bit ARM and FreeBSD hosts (B16)

`src/shared/app-knowledge.ts` has a known-issues entry: those hosts run an SSH Persistent session without tmux persistence unless tmux is installed from the host's packages, and the session resumes with `--continue`. No code change: there is no upstream binary to pin.
