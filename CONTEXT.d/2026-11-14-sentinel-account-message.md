## 2026-11-14 -- Sentinel says the right thing when its analysis account cannot run

**Problem (owner report, 2.1.3-beta.1).** With the analysis account's login expired, the Sentinel panel said the account "has hit its usage limit", called it "auto-picked, your chosen analysis account is no longer available" although Settings showed the default account, showed the whole message twice, and ended the CLI's own remedy in the middle of a sentence.

**Four faults, four causes.**
- *Usage limit.* `envelopeError` (`src/main/sentinel/sentinel-analysis.ts`) counted any word "limit" as a usage limit. Claude Code's text for a login that ran out says it "reached its time limit". Now a sign-in failure is its own kind (`signIn`): a 401, or the CLIs' own sign-in words (failed to authenticate, token expired, not logged in, sign in again). A "time limit" is no longer a usage limit. A 429 is still always a usage limit, and a sign-in that could not reach the service is still said as unreachable.
- *Auto-picked.* The label compared the saved choice with the account used and nothing else. A saved choice whose account was since removed shows as "Primary account (default)" in Settings, but the message reported it as a chosen account that was no longer available. The label is now built in `src/main/sentinel/sentinel-account.ts`: it names the account used and why (chosen in Settings, the primary account, auto-picked because no primary account is set), and says "auto-picked, your chosen analysis account is no longer available" only when an account Settings still lists as chosen could not be used. Codex had the same fault: a saved Codex choice that Settings no longer offers is now the default there too, is not tried, and the account is named "the Codex review account". Settings and the main process read one rule for which Codex accounts are offered (`sentinelCodexAccountOffered`, `src/shared/providers/accounts-view.ts`).
- *Twice.* A run analyses each update (Claude Code's and Codex's) on the same analysis account, so one account failure produced the same sentence once per update, and the panel joined them. A message already said in a run is not said again (`analyzeUpdates`, `src/main/sentinel/index.ts`). Different problems in one run are all still said.
- *Cut short.* The reason was cut at 160 characters wherever that fell. A sign-in failure now keeps only what went wrong (the CLI's first sentence) and gives this app's own remedy in full: sign the account in again from its card on the Usage page, or pick a different account in Settings, Sentinel, then Re-run. The CLI's "claude auth login" is not echoed: it signs in the user's home folder, not the account's own folder. Any other long reason keeps the whole sentences that fit and drops the one that does not, so it never ends half way through one.

**Also.** An expired login is not tried a second time in the same analysis, as a usage limit is not.

**Not changed.** The usage-limit and unreachable messages, the timed-out wording, which account an analysis runs on (except that a Codex choice Settings no longer offers is not tried first), and the Settings page.

**Tests.** `tests/unit/sentinel-account-message.test.ts` (new, the pure rules) and new cases in `tests/unit/main/sentinel-codex-service.test.ts` (the real service: once per run, the labels through to the panel text). Before the change 6 of the new service cases failed, among them "expected 2 to be 1" for the message count. 21 mutants of the changed logic, one at a time, all killed.
