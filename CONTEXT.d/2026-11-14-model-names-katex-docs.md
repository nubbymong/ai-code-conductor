## 2026-11-14 -- Model names, the katex override and stale stack versions (2.1.3-beta.3, item E)

One branch, three small things.

### Model names (planning #310)

The cases the same day's matching change left open (`2026-11-14-model-match-longest-pattern.md`, "Not done here"). All three are one mistake: a name went to another version's entry.

**A dated id read as the next version.** A name that is no entry's id or alias goes to the longest id it starts with. `claude-fable-5-20260101`, the dated id of Fable 5, starts with `claude-fable-5-2`, so it was shown as Fable 5.2. Tokenomics picks a price key the same way, so the turn was priced as Fable 5.2 as well. Now an id that ends in a digit is not the start of a name whose next character is a digit too: the number carries on, so it is another number.

**A version written with a dot, behind a gateway's name.** A gateway writes `anthropic/claude-opus-4.7`. The version patterns are written with a hyphen (`opus-4-7`), so none was found in such a name and it went to the entry with the family's plain pattern: Opus 4.7 was shown as Opus 5.5. The pattern step now reads the name two ways, as written and with each dot between two digits as a hyphen, and the reading that covers more counts. Each reading keeps the rule that a pattern which stops inside a version number does not count, so `anthropic/claude-opus-4.75` and `anthropic/claude-opus-4.7.1` are not Opus 4.7. A pattern that is itself written with a dot is still found in the name as written.

**A version written with a dot, with nothing around it.** The id step comes before the pattern step, and it read the name only as written. `claude-opus-5.5` as written starts with `claude-opus-5` and no longer id (a dot follows, not a digit), so it was Opus 5, by a match the app trusts for a label, a price and an effort list. `claude-sonnet-5.5`, `claude-fable-5.2` and `claude-fable-5.1` went to their base models the same way. The id step now reads the name the same two ways. The longest id of either reading takes the name; of two as long, the one the name as written starts with. So for the Claude models the build ships, whose ids are all written with hyphens, a name written with a dot goes to the entry the same name written with a hyphen goes to.

That holds for those models and no further. A model only a fetched model file has is tried after every standing entry, an order this change keeps. So with a fetched `claude-opus-6-1`, the name `claude-opus-6.1` is not that model: the family's plain pattern takes it first, and it goes where the build alone puts it, Opus 5.5. (In a family nothing shipped places, the dotted name does reach the new model by its id. In a shipped family the file can list the dotted name as an alias of its model: see the fetched model file, below.) And an id that is itself written with a dot is not the same id written with a hyphen: `gpt-5.5` is a model, `gpt-5-5` is not.

One helper, `longestIdNameStartsWith` in `src/shared/model-registry.ts`, holds both id rules (where an id ends, and the dot). It serves the matcher and both price-key lookups (`toPriceModel` in `src/main/tokenomics/tk-parse.ts`, `normalizeModelForPricing` in `src/main/tokenomics/tk-pricing.ts`), so the three cannot disagree.

**What moves, against the bundled file.** Each line gives a name, where it went before this branch, and where it goes now. A match by id (an exact id, an alias, an id the name starts with) is one the app trusts for the label, the effort list and the row the picker marks. A match by pattern is not: every effort level is offered for it.

The dot rule (only a dot between two digits is read as a hyphen):

- `claude-opus-5.5`, `claude-sonnet-5.5`, `claude-fable-5.2`, `claude-fable-5.1`, with or without a date or `[1m]` after them: were the base model (Opus 5, Sonnet 5, Fable 5), by its id. Now their own entry, by its id.
- `claude-opus-4.7`, `claude-sonnet-4.5` and the other older two-part versions, with or without a date or `[1m]`: were the entry with their family's plain pattern (Opus 5.5, Sonnet 5.5), by pattern. Now their own entry, by its id.
- `claude-opus-4.7.1`: was Opus 5.5, by pattern. Now Opus 4.7, by its id, as `claude-opus-4-7-1` always was.
- Behind a gateway's name (`anthropic/claude-opus-4.7`, `anthropic/claude-fable-5.2`): were the entry with the family's plain pattern (Opus 5.5, Fable 5). Now their own entry, still by pattern. A three-part version there (`anthropic/claude-opus-4.7.1`) stays with the plain pattern.
- In Tokenomics a model written with a dot and nothing around it takes its own price key. The 5.x names took their base model's key (Opus 5.5 was priced as Opus 5, Fable 5.2 as Fable 5). The older ones started with no key and had no price.

The digit rule (an id that ends in a digit is not the start of a name whose next character is a digit). It moves every name that is a shipped id with a digit straight after it, not only the dated id of Fable 5. Each of these was the model whose id it starts with as text, by its id:

- `claude-fable-5-20260101`: was Fable 5.2. Now Fable 5, by its id.
- Where a shorter id ends where the number does, that model takes the name, by its id. `claude-opus-5-50` was Opus 5.5 and is Opus 5. `claude-fable-5-25` was Fable 5.2 and is Fable 5.
- Where none does, the family's plain pattern takes it, by pattern. `claude-opus-4-75` was Opus 4.7 and is Opus 5.5. `claude-sonnet-4-55` was Sonnet 4.5 and is Sonnet 5.5. `claude-haiku-5-50` is still Haiku 5.5, by pattern now.
- Codex: `gpt-5.25` and `gpt-5.50` were `gpt-5.2` and `gpt-5.5`, by their ids, and took those models' effort levels. Now only the catch-all pattern places them, so they are held as a model the registry cannot place and every Codex level runs for them. This loosens the effort check at launch for such names: a launch on `gpt-5.55` with `max` used to drop the effort (`gpt-5.5` has no `max`) and now keeps it. None of these names is a model the Codex catalogue lists.
- In Tokenomics such a Claude name takes the shorter price key when there is one (`claude-opus-5-50` was priced as Opus 5.5 and is priced as Opus 5) and has no price when there is none (`claude-opus-4-75` was priced as Opus 4.7).
- A contrived name can change family. With no id to hold it, the first pattern in list order places it: `claude-opus-4-75-fable` was Opus 4.7 and is Fable 5; `gpt-5.25-opus` was `gpt-5.2` and is Opus 5.5.

Against the bundled file nothing that was placed is unplaced: every shipped Claude id has its family's plain pattern in it, and every shipped Codex id starts with the catch-all's (`gpt-`). Apart from contrived names like the two above, no name changes family.

**The fetched model file.** `src/main/model-registry-data.ts` asks the matcher where the build places a name, so what a fetched file may carry follows the matcher. Two files change sides with it, and both are meant:

- Taken now, refused before: a new `gpt-5` with the alias `gpt-5.55`. The build no longer puts `gpt-5.55` on `gpt-5.5` by its id, and an alias that starts with its model's own id is that model's name.
- Refused now, taken before: a new `claude-opus-4` with the alias `claude-opus-4.7`. That name is Opus 4.7's now.

One rule is added, so that the check reads a name as the matcher does. A shipped id written with a dot (`claude-opus-5.5`, `claude-opus-4.7`), or a dated or `[1m]` form of it (`claude-opus-4.7-20260101`), is that shipped model's name by a match the app trusts. A new model is refused it, as its id and as an alias, as it is refused the same name written with a hyphen. Without the rule a file could take those names: the hyphen form was refused and the dot form was not. The same reading is used where an alias is held against its own model's id: `claude-opus-4.8-f` does not own `claude-opus-4.8-fast-x`, as `claude-opus-4-8-f` does not own `claude-opus-4-8-fast-x`. A new model written with a dot that is no shipped name stays free (`claude-fable-5.3` with `claude-fable-5.3-20270101`).

A second review round found the reading was used on one side only. An alias is a new model's own name when it starts with that model's id, and that was asked of the two as they are written. So a new `claude-opus-5-7` could not list `claude-opus-5.7` or `claude-opus-5.7-20270101`, and a new `claude-opus-5.7` could not list `claude-opus-5-7`: the file was refused, naming `claude-opus-5`. A new model in a shipped family is tried after every shipped entry, so an alias is the file's one way to have the name a gateway writes. Without it the name stayed on the older model whose id it starts with, by a match the app trusts for a label, a price and an effort list. Now the alias starts with its model's id when it does as the two are written, or as the two are read with each dot between two digits as a hyphen.

The shipped id is held against the new one in both readings as well, so the wider rule gives a file no shipped name. Of two ids that both start the name, the shipped one keeps it unless the new one is longer. `gpt-5-5` does not own `gpt-5.5-x`, which carries on from the shipped `gpt-5.5`; `claude-opus-4.8-f` does not own `claude-opus-4-8-fast-x`. An exact shipped id or alias, a dated or `[1m]` form of a shipped id and a shipped id written with a dot are refused before this is asked, as they were. That round refused no file that was taken before it.

A third round found one reading the check still did not have. The matcher finds an id in a name as the id is written, and never reads a hyphen as a dot. The Codex ids the build ships are written with a dot, so `gpt-5-6-sol` starts with no shipped id and only the catch-all pattern places it. An alias that starts with its model's own id is let past a pattern, so a new `gpt-5.6` or `gpt-5-6` could list `gpt-5-6-sol`, `gpt-5-6-terra` or `gpt-5-6-luna-20260101`: a longer shipped model's name in the other spelling. For an alias that starts with its model's id, the shipped ids are now read with a dot as a hyphen as well, and the two rules that hold where the matcher does find a shipped id hold in that reading:

- A dated or `[1m]` form of a shipped id is that model's, however long the new id is. `gpt-5-5-20260101` is not a new `gpt-5.5-`'s.
- Of two ids that both start the alias, the shipped one keeps it unless the new one is longer. An id starts a name as the matcher has it, not where the number carries on: `gpt-5-55` is not held for `gpt-5.5`.

The reason names the shipped model the alias spells (`gpt-5.6-sol`), not the catch-all entry. Only an alias is held to this. Where a name goes is not changed, and a new model may still have `gpt-5-5` as its id.

Refused now, taken before, and meant:

- A new model whose id is shorter than a shipped one, with that shipped model's name, or a name that carries on from it, written with a hyphen: `gpt-5.6` or `gpt-5-6` with `gpt-5-6-sol`, `gpt-5` with `gpt-5-5`.
- A new model whose id is a shipped id written with a hyphen, with a name that carries on from it in the same spelling: `gpt-5-5` with `gpt-5-5-x`. The second round's tests had this file as taken. It is the tie the rule gives the shipped id, as `gpt-5.5-x` on the same model already was.
- A new model of any length with a shipped model's dated id written with a hyphen: `gpt-5.5-` or `gpt-5-5-2026` with `gpt-5-5-20260101`.

Still taken: a new model's own id written the other way beside those shipped ids, and the names that carry on from it (`gpt-5.6` with `gpt-5-6`, `gpt-5-6-mini` and `gpt-5-6-20270101`), and a longer id of its own (`gpt-5.5-pro` with `gpt-5-5-pro`). No shipped Claude id is written with a dot, so nothing changes for a Claude model.

**Not done here.**

- Turns Tokenomics has already stored keep the price key they were given when they were read, and a daily, hourly or per-session total keeps the key of the first turn it counted. So a dated Fable 5 turn read by a build that had the Fable 5.2 entry (#663) and not this change is still priced as Fable 5.2, and so are later turns of that model counted into the same totals. The Codex re-key at every open (`src/main/tokenomics/tk-db.ts`) is not a pattern for this: a Codex key is the model's own name, which the database can work out alone. A Claude key depends on the price list, which the database does not have when it opens and which changes when the fetched prices arrive, so "the key this model would take now" would move rows back and forth between a built-in key and a fetched one. It needs its own design: which list a stored key is held to, and whether a total should keep a key at all.
- Tokenomics has no pattern step. A gateway's or a partner platform's name that starts with no price key has no price, as before.

### katex override

mermaid pins katex `^0.16.45`, which has a public low-severity advisory; the patched line is 0.18. `package.json` now overrides `katex` to `^0.18.2`, and the lockfile resolves 0.18.10 (0.18.11 is marked deprecated upstream). This closes the item the beta.2 dependency note left for the next beta.

- Where it is used: the app source names neither katex nor mermaid. The only path is the Agent Canvas drawing library, whose Mermaid import loads mermaid, which loads katex only when a diagram's text holds a `$$...$$` span.
- What mermaid asks of it: one call, `renderToString`, with MathML output. Checked side by side with 0.16.45: the MathML output is the same, and the `katex` class mermaid's one style rule names is still there. The 0.18 line renamed some inner HTML classes, which the app does not style.
- katex 0.18 depends on a newer `commander` for its own command-line file, which nothing here runs. It asks for a newer Node than CI uses, so an install may print an engine warning; nothing fails on it.
- `tests/unit/katex-output-shape.test.ts` pins that one call in terms both lines share: the outer `katex` span with MathML inside and no HTML tree, an error on input katex cannot read, and no link from a `javascript:` address unless a caller trusts the input. It names no version or inner class, so it runs on whichever katex is installed. Its checks pass on 0.16.45 and on 0.18.2; CI installs 0.18.10.
