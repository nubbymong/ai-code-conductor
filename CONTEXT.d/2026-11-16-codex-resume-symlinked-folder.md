## 2026-11-16 -- Codex resume and resume list match a symlinked folder by real path (2.1.3-beta.6, plan section E)

**Problem.** A Codex conversation started in a symlinked folder (a symbolic link on macOS and Linux, a junction or link on Windows) records the link or the real folder, and the tab keeps the other. The resume lookup (`sameDirectory` in `providers/codex/rollout-lookup.ts`) and the resume list (`samePath` in `scripts/lib/codex-resume-picker-lib.js`) compared the spelling only. So the lookup set `cwdMismatch` and started in the configured folder (a resume by id still worked), and the list did not offer the conversation at all. beta.5 fixed the status-line claim only and left this as a follow-up (`2026-11-15-accounts-and-sessions-307.md`, "Not in this change").

**Change.**
- The folders are compared by exact spelling first. Only when that finds no match is the real path asked, with `fs.promises.realpath` (never the synchronous call), for the tab's folder and every distinct recorded folder together, with one bounded wait (`CODEX_REAL_PATH_WAIT_MS`, 1.5 s, the repo's `withPathWalkDeadline`). A rollout that records the tab's folder as spelled makes no real-path call at all. A path that cannot be resolved (missing, refused, no answer in time, relative, or a share written as `\\server\share` or `//server/share`) is compared by its spelling alone, as before. A folder on a mapped drive letter looks local, so it is asked, bounded.
- Across lookups (several tabs restored together, every launch): a folder still being asked is not asked again, and a drive that did not answer is left alone for 60 s (`CODEX_DISK_SILENT_MS`), ended early if the call that did not answer answers after all. On macOS and Linux the "drive" is the mount (`/Volumes/x`, `/mnt/x`, `/media/u/x`, `/run/media/u/x`, `/net/x`), else the root disk, so one stale network mount does not silence the rest. This keeps a dead drive from using up libuv's four threads.
- Resume lookup: the launch builder (`buildCodexSpawn`) is synchronous and `pty-manager.ts` may not grow, so the look is made where the launch already waits for the node.exe lookup: `ipc/pty-handlers.ts` awaits `provider.warmResumeLookup` (new, optional) before `spawnPty`. `warmCodexResume` finds the conversation's rollouts, compares by real path, and also works out, with the same bounds, whether the tab's folder is a folder and whether it is the home folder or above it (`isHomeOrAncestorAsync` in `path-utils.ts`: the same rule as `isHomeOrAncestor`, checked against it by test; not asked when the tab's folder is the configured one, which the builder never guards). It keeps the answer for 30 s, per realm, session, conversation and folder. `resolveCodexResume` reads it once and then asks the disk nothing: no `statSync`, no `realpathSync`. A check that does not answer in time counts as "not usable", so the launch starts in the configured folder. With no answer kept (no warm-up, it ran out, or it is for another session) the builder walks, compares the spelling and asks the disk in place, exactly as before.
- The walk of the sessions folder (`findCodexRollouts`) is still synchronous. It runs once in the handler, and once more in the builder only if the warm-up's answer was not read. It used to run in the builder, so the main thread reads no more than before.
- Which conversation is warmed mirrors `pty-manager.ts`: the request's own `resume`, else on a restart the kept one, never after the picker or a fresh-conversation respawn; an Ask launch is left to the spelling.
- Resume list: `walkRolloutsAsync` (new, the picker script awaits it) lists a rollout whose recorded folder is the same real folder as the session's folder or a git worktree. Worktree real paths are asked only when a rollout does not match by spelling. After one folder does not answer in time, no new folder on the same drive (on macOS and Linux, the same mount) is asked, while an answer already had is still given. There is no second spelling-only walk to fall back to: the async walk does not reject on a folder it cannot resolve, and anything else it throws is what the picker's `main().catch` already turns into a fresh launch. `walkRollouts` itself is unchanged (it now shares the new `rolloutHeads` generator).
- Status-line claim: unchanged, and it stays on the synchronous call on purpose. `sameFolderByRealPath` (`telemetry.ts`) runs inside the claim's polling, which is synchronous; each folder is asked once per watch. That is beta.5's behaviour and it is not bounded. Moving it to the async helper means making the claim itself async, which is a separate change to its poll loop and identity rules. It only shares the new `isLocalAbsolutePath` rule.

**Tests.** `tests/unit/providers/codex/resume-real-path.test.ts` and `tests/unit/scripts/codex-resume-picker-real-path.test.ts` (a stand-in for the real path, run anywhere: spelling first with no call on a spelling match, one wait for every folder, once per folder, the memory across lookups, the checks, read once, freshness, the session, the cap and the sweep, case on Windows, no synchronous call). `tests/unit/providers/codex/resume-warm-wiring.test.ts` (the provider's warm-up and `buildSpawnCommand` agree on the key: realm, session, conversation, folder). `tests/unit/main/pty-spawn-warms-codex-resume.test.ts` (the real `pty:spawn` handler with a stand-in provider: it waits for the look, names the request's own or the kept conversation as pty-manager does, passes the session and the configured folder, skips the picker, a fresh respawn, SSH and Ask, and survives a look that fails). `tests/unit/main/path-utils-home.test.ts` (the async home guard gives the sync guard's answer). `tests/unit/providers/codex/resume-real-path-links.test.ts` (host quarantine: a real symlink on macOS and Linux, a real junction on Windows, both ways round, a link whose folder is gone, the list, and no synchronous real-path or stat call). The links file has only run in CI; the Windows junction case is its first Windows run.
