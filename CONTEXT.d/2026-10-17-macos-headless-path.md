## 2026-10-17 -- Headless Claude Code runs find Claude Code when macOS opens the app from the Dock

**Problem.** A macOS app opened from the Dock or Finder gets launchd's PATH (`/usr/bin:/bin:/usr/sbin:/sbin`). Off Windows, a headless run (the setup version check, Insights, Sentinel's checks) started `sh -c claude ...` with the app's own PATH, so it exited 127 when Claude Code lived in `/opt/homebrew/bin` or `~/.local/bin`. The CLI probe found it all along, because it asks the login shell (`<shell> -lc 'command -v claude'`), so setup said "installed" and "couldn't read the version" on the same page.

**Change.** `src/main/claude-cli-probe.ts` keeps the path a probe found, and lets a caller see the probe still running. `src/main/claude-headless.ts` puts that path's folder first on the run's PATH when PATH does not already name it (`withClaudeFolderOnPath`). A known path is used at once, even while a later probe runs. While no Claude Code is known (no probe has found one yet, or the last answer was a plain "not found"), a run waits for a probe already running: Sentinel's check at start runs while the start-up version probe is still asking. That wait has a bound of 25 s, after which the run starts without the answer, as before: a probe whose processes end on their timeouts answers within it, and the whole start stays inside the 60 s grace of a profile run's consumer hold. An abort ends the wait at once and starts nothing. With none known and none running, a run starts as before. A run with no profile home starts no login shell of its own. One under a profile home can: composing its environment records the managed launch's preflight, which starts the version probe (and with it a CLI probe) while the version is unknown, and the run then waits for that probe.

**Hardening from the adversarial pass.**
- A probe whose login shell gives no answer to go by (ended by its timeout, could not start, printed nothing) keeps the path found before, while that file is still there. Only the login shell's plain "not found" clears it. A probe that throws keeps it too.
- The login-shell probe runs in the home folder, as the login shell's PATH question already did, so a relative PATH entry cannot resolve inside the folder the app was started in.
- Only the login shell's answer is kept for a run, and only when a run may put it on PATH: absolute, a last part that is exactly `claude`, and no `:` or control character (C0, DEL, C1, or a Unicode line or paragraph separator) in its folder. A stray line a login profile printed, or an answer of `which`, leaves the path kept before. `which` searches the app's own PATH from the app's folder, and GNU which answers a relative entry with a full path under that folder. The probe still reports both for its other uses.
- Each probe process settles 1 s after its 8 s timeout even when it ignores SIGTERM, and is then ended with SIGKILL, so a hung login shell no longer holds the probe, and with it every later run's wait, for the life of the app.

**Known and not changed.**
- A folder the user's own PATH lists late (after `/usr/bin`, say) goes first for the run, so every program in it is found before the system's.
- A kept folder that another user deleted and made again under a shared parent anyone may write to (a sticky one such as `/tmp`) is still used while a file named `claude` is there; who owns it is not checked.

**Where PATH changes.** A Dock or Finder start gets launchd's bare PATH, the case this fixes. An app started from a terminal (Linux, or macOS) keeps that terminal's PATH unchanged only when it already names the probe's folder. Otherwise that folder goes first, so the run starts the Claude Code the login shell names (as an interactive session does), which can differ from the one the inherited PATH would find.

**Kept as it was.** `shell: true`, the argv refusals (`assertSafeArgv`), the Windows start, interactive sessions, and every other provider. The folder is the one the probe named, not the link's target, so an npm install (`#!/usr/bin/env node`) finds the node beside it.

**Tests.** `tests/unit/claude-headless-posix-path.test.ts` has 40 cases. Eighteen are POSIX only (skipped on Windows), and fourteen of those start a real `sh -c claude` into a fake Claude Code under a bare PATH and an environment built from nothing. Three of the first five fail on the code before this change with `claude: not found` (exit 127), and the case for a run that waits for the probe also fails when only that wait is removed. The other thirteen cover the hardening: a probe that never answers (the run starts after the bound), one that answers within it (the wait clears its timer), an abort during the wait (answered at once, nothing started), runs that waited and ended with no abort (the wait leaves no listener on the signal), a timed-out probe that keeps the path, a plain "not found" and a vanished file that clear it, a login shell that never exits (the probe still settles and ends it), three answers a run may not use that leave the good path kept, a profile line that is not `claude`, and two answers of `which` that are never kept. Twenty-two cases run on every OS and start nothing. One forces `win32` and fakes the Windows lookup and start command, and proves a Windows run neither waits for a running probe nor uses its last answer, and hands the Windows start its PATH unchanged; it fails when the POSIX prepend, or the wait, is applied on Windows too. One reads the working folder the probe hands its login shell. Twenty cover `withClaudeFolderOnPath` itself. Each hardening fix was reverted on its own, and each time at least one of its cases failed.
