## 2026-11-17 -- Service overhead harness for the Windows test VM (2.1.3-beta.7, plan section B1)

**What.** `scripts/perf/` measures what each part of the app costs on the test VM, idle and busy, with 1, 10 and 25 sessions, against the installed build on a README staging root (started from SSH through WMI, so in session 0, with `--dom-terminals`). `run-matrix.cjs` runs the grid and the ablations (Tokenomics, session logging and the hooks gateway each switched off at N=25 busy, between two all-on runs); `report.cjs` turns one or more results folders into the per-service tables. It runs only on the test VM: a Hyper-V guest with `CCC_PERF_TEST_VM=1` set. Nothing here is packaged. `scripts/readme-shots/stage/fake-claude.js` takes a `mode` (idle or busy) and a `copies` map from its `fake-stage.json`, through `fake-mode.js`; with no mode in that file, as in the README pipeline, it runs as it did before.

**Decisions, from the VM runs.**
- CPU comes from each process's cycle count (QueryProcessCycleTime, through PowerShell's Add-Type: nothing installed). Windows charges user and kernel time by sampling at the 15.6 ms clock tick, which misreads processes that run in short timer-driven bursts, low or high: at N=25 busy the console hosts read 0.03 % of a core from those times and 3.44 % from their cycles, the renderer 3.65 % and 23.20 %, Defender 1.50 % and 10.70 %, but the GPU process 6.14 % and 3.66 %. The app's own figure (`app.getAppMetrics()`) agrees with the cycles for its processes (renderer 23.21 %). The report marks any cell that is not from the cycles.
- Electron runs Node's loop inside its own, so `performance.eventLoopUtilization()` reads zero in main. Main's JS thread share comes from its CPU profile instead, and the profile covers that thread only. At N=25 busy the whole main process used 5.61 % of a core while its JS thread was 1.2 % busy (12.0 ms per second; run 2: 5.20 % and 1.0 %), so most of main's CPU (Chromium's browser-process threads for I/O, IPC and the thread pool) is not attributed by this harness.
- Main is bundled into `out/main/index.js` and chunks, neither minified nor source-mapped. `service-map.json` attributes a frame by its own name or by the top-level function or class it sits in, read from the bundle's files, with one row per Services registry row that runs in main. Of the JS thread's busy time at N=25 busy: services 63.9 %, garbage collection 1.5 %, native code outside JS 16.1 %, not attributed 18.5 % (run 2: 69.7, 1.6, 11.2 and 17.1 %).
- A resumed tab starts its terminal only when it is first opened, so Resume alone starts one session whatever N is. The runner opens each card once and measures only once N session CLIs (started with `--resume`; the app's probes are not sessions) run at once.
- Every run starts from the seed: `gen-sessions.cjs` keeps the seeded transcripts and the Tokenomics and session logging databases on its first run, and puts them back before every run, so no run (the ablations included) reads files an earlier run's writer grew.
- Every window settles 5 minutes first, as the plan sets: the busy window follows the idle one on the same app start, but the transcript writer and the busier CLIs start only at the switch, and the Tokenomics worker walks every transcript once every 5 minutes. The report estimates for each window whether a walk falls inside it.
- The noise each conclusion is read against: the ablations run between two all-on runs, the reduced-motion test runs as A/B/A (as is, reduced, as is) after a 15 s gap, and the N=25 runs and the ablations ran twice. N=1 and N=10 ran once. Given several results folders, `report.cjs` reads the ablation savings once, against every folder's all-on windows together, and gives no verdict from fewer than three all-on windows (one folder has two, and run 1's two agreed within 0.04 by chance).
- Raw CDP over Node's own WebSocket, not Playwright: nothing to install on the VM, and no domain switched on beyond the ones a reading needs.
- Copies of the seeded sessions draw their template's scenario, but their status names their own transcript, so session logging and usage attribution follow N files, not one (an early run bound every copy to the same file and was thrown away).

**Baseline, installed 2.1.3-beta.6, harness at 1588c81b** (the commit the VM ran; after this branch's rebase onto beta it is 417dd41d, with the same harness files. The figures are `report.cjs` at 87631fec over the two saved results folders: its service map and its ablation reading are newer than the VM's, the samples and profiles are the VM's. VM: 12 logical CPUs, 8 GB, software GL; % of one core; 3-minute windows after a 5-minute settle; run 1 the full grid from 02:52Z, run 2 the N=25 runs and the ablations from 04:36Z, both on 17 Nov; a pair is run 1 then run 2):
- N=25 busy: app 33.65 and 31.00: renderer 23.20 and 21.43, main 5.61 and 5.20, GPU 3.66 and 3.26, Tokenomics worker 0.48 and 0.45, session logging worker 0.29 and 0.27, hooks gateway worker 0.04, vision browser 0.37 and 0.35. The terminals (shells, console hosts, fake CLIs) add 7.11 and 6.89, Defender 10.70 and 9.98. Renderer main thread 15.0 and 13.8 % busy (CDP task time).
- N=25 idle: app 7.82 and 6.12 (renderer 5.49 and 4.24, main 1.19 and 1.01, GPU 0.55 and 0.39). N=10 (run 1 only): 3.36 idle, 23.36 busy. N=1 (run 1 only): 1.32 idle, 12.58 busy.
- Ablations at N=25 busy: no saving clears the noise. The four all-on windows read 35.29, 35.25, 34.57 and 33.26 (a spread of 2.03; 0.04 within run 1 and 1.31 within run 2). Against their mean (34.59), the two runs' means save 0.36 with Tokenomics off, -0.14 with session logging off and 0.07 with hooks off, all "no" in the report's table across the two runs, and each switched-off cell differs by 0.35 to 1.51 between the runs. The grid's own busy window reads lower than the ablation runs' all-on windows in both runs (it follows the idle window, its profiles and its A/B/A on the same app start, where each ablation run starts the app afresh), so read each ablation against the all-on windows only. The reliable per-service figure is each worker's own CPU: Tokenomics 0.45 to 0.64, session logging 0.27 to 0.35, hooks gateway 0.04 % of a core across the N=25 busy windows with the service on, plus their share of main's JS thread (run 1: Tokenomics 1.92, session logging 0.83, hooks 0.05 ms per second).
- The renderer is the cost. Its top self-time function at N=25 busy is `formatResetTime` (7.97 ms per second of 144 ms busy; run 2: 8.69 of 129), almost all of it under `RateLimitBar` (8.32 ms per second inclusive, 0.30 self). In main's JS thread: terminal I/O 2.24, statusline 2.13, Tokenomics (main side) 1.92 and session logging 0.83 ms per second.
- `prefers-reduced-motion` A/B/A at N=25 busy, renderer: 23.19, 14.84, 21.36 (run 1) and 22.56, 14.41, 20.24 (run 2). The reduced part is 5.8 to 8.4 points below either as-is part, while the two as-is parts differ by 1.83 and 2.32 (drift). GPU 3.60, 0.79, 3.64 and 3.57, 0.72, 3.35; style recalculations about 38, 19 and 32 per second. At N=25 idle the renderer reads 6.53, 4.13, 5.97 and 4.93, 3.38, 5.15. On the VM's software GL the always-on sidebar animations are about a third of the renderer's CPU at N=25 busy; how much of that a desktop GPU shows is not measured here.
- Tokenomics (aicc_planning#302 acceptance: under 5 % of one core with 20+ working sessions): the worker used 0.45 to 0.64 % across the ten N=25 busy windows with it on, its Services row's own figure agreeing (0.4 to 0.6 %), while it ingested 5.0 events per second (one per transcript line). A full walk was expected inside each run's grid busy window (0.48 and 0.45 there). The VM's transcript tree is 64 files, not a desktop's thousands, and the fake CLI is not Claude Code.
- The first baseline in this PR (5d054eb9, an earlier revision of the branch, before the review fixes) read N=25 busy app 43.6 %. It ran with a 90 s busy settle, with runs building on each other's transcripts, and before the cycle counts; the figures above replace it and are not compared with it.

**Not comparable to a desktop.** Session 0 forces DOM terminals and software GL, so renderer and GPU figures are not the owner's WebGL figures; read the numbers as relative between windows.

**Not in this change.** The fixes the numbers point at belong to B2 and B3 (statusline tick churn, hidden-terminal writes). For B2: `RateLimitBar`'s self time read 17.8 and 14.1 ms in the 60 s profiles at N=25 busy, and its inclusive time 499 and 547 ms, almost all `formatResetTime`. For B3: `handleSelectionChanged` did not appear by that name in any of the VM's renderer profiles (DOM terminals in session 0). The always-on animations are not in either.
