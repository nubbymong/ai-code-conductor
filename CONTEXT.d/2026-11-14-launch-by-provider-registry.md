## 2026-11-14 -- A local launch picks its assistant from the provider registry (2.1.3-beta.3 item D, planning #310)

**Problem.** On the local path the PTY manager told the two assistants apart by one name test: a session naming Codex took the Codex branch, and every other session took the Claude Code branch. A session naming an assistant the app does not know would have started Claude Code in its place (pty:spawn's schema refuses such a name first, so the app could not send one; the PTY manager had no rule of its own). pty:spawn asked whether an assistant's sessions run on another machine only when the session named Codex, though the accounts service answers that for any assistant from what its package declares. And a launch the PTY manager holds (while the account's sign-in is refreshed, then while the project's settings are checked) started when the wait ended without asking main's launch rule again (planning #310).

**Change.**

- `src/main/pty-manager.ts`, local path only. A local launch that starts an assistant looks it up once (`localLaunchOf`): the id must be one the app knows, a provider must be registered for it, the registered package must declare session launches (`session.launch`), and the PTY manager must have a way to start it (`LOCAL_LAUNCH_STYLE`, one row per provider id: `direct` for Codex, `shell` for Claude Code). Anything else is refused with a plain sentence and nothing starts; no assistant starts as another. The two local branches are chosen by that row, and each uses the provider the registry returned. A terminal tab starts no assistant, is not asked, and opens as before.
- The run a launch is indexed under is recorded from the provider that was looked up.
- `deferSpawnUntil`: when a wait ends, a held launch that starts an assistant asks main's launch rule again (`providerLaunchRefusal`). Refused (switched off meanwhile, or the setting cannot be read, or there is no accounts service to ask): nothing starts, the terminal shows the rule's sentence before the exit, and the hold on the account is released, through the exit a failed re-entry already takes. Both waits ask, one after the other.
- `src/main/ipc/pty-handlers.ts`: an SSH spawn asks the accounts service's `remoteLaunchRefusal` about whichever assistant it starts, and a terminal tab over SSH about the one it names when it names one. With no accounts service the registry's own `session.ssh` declaration answers, so a terminal tab naming Claude Code still opens then. Claude Code declares SSH sessions and Codex does not, so what each is told is unchanged.
- `src/main/providers/index.ts` re-exports `providerCapability`, the route the launch path already uses to reach the registry.

**Not changed.** The SSH branch of the PTY manager (its own name check and its use of the Claude Code provider) is left for the remote redesign. `deferSpawnUntil` is called only from the local branch, so the new question is never asked for an SSH launch. One name check on the shared tail (`runProvider`, which picks whose saved logging switch applies) also runs for SSH launches and was left as it was.

**Ratchet.** `tests/unit/architecture/provider-name-ratchet.test.ts` counts, in `src/main` outside `src/main/providers`, comparisons of a provider id with a name (71 before this change, 69 after) and ids defaulted to a name in place (27 before and after). A count above its ceiling fails and names the files; a count below it fails and asks for the ceiling to be lowered, so the numbers only go down.

**Tests.** New: `pty-local-launch-registry`, `pty-held-launch-provider-off`, `pty-spawn-remote-capability` (all under `tests/unit/main`), and the ratchet. 20 of their cases failed before the change. Tests that stand in for the provider registry now also answer the capability question (one line each), two that registered a bare Claude Code session provider register its package, and tests that drive a held launch through the real PTY manager stand in for the launch rule, as tests of pty:spawn already do.
