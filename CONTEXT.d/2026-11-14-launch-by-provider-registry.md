## 2026-11-14 -- A local launch picks its assistant from the provider registry (2.1.3-beta.3 item D, planning #310)

**What this does.** A local launch that starts an assistant looks it up in the provider registry, and that one lookup decides the launch: which provider starts, how it is started, and whether its sessions start on this computer at all. The lookup is made before anything of the session is touched. pty:spawn asks the matching question for a launch on another machine about whichever assistant it starts. A launch the PTY manager holds (while the account's sign-in is refreshed, then while the project's settings are checked) asks main's launch rule again when each wait ends (planning #310). This is consistent with how the accounts service gates every other capability (one answer, from one place, for each question a launch asks), and with the rule the saved accounts list, profiles.json, follows since PR #657: what is refused, or has no answer, changes nothing.

**Change.**

- `src/main/pty-manager.ts`, local path only.
  - The lookup (`localLaunchFor`, which calls `localLaunchOf`) is asked by each caller of `spawnPtyResolved` before it runs and is handed down: a launch asked for directly, one pty:spawn prepared first, and one that goes on after a wait (which is looked up again then). The id must be one the app knows, a provider must be registered for it, the PTY manager must hold a way to start it (`launchStyleOf`), and its sessions must start on this computer. Anything else is refused with a plain sentence: nothing starts, and no assistant starts as another. A launch that is refused there has taken no held launch's place, ended no running process and read no conversation to resume. A terminal tab starts no assistant, is not asked, and opens as before.
  - How each provider is started is its row in `LOCAL_LAUNCH_STYLE` (exported): `direct` for Codex, `claude-shell` for Claude Code. `claude-shell` is Claude Code's own launch and no other provider's: `launchStyleOf` gives that row to Claude Code alone, and the branch that runs it refuses any other id with the same sentence.
  - Whether a provider's sessions start on this computer is the accounts service's answer (`AccountsService.localLaunchRefusal`: its `session.launch` capability on this platform, with the experimental declarations the owner enabled for that provider). With no accounts service to ask, the registry's own declaration answers, with nothing experimental enabled.
  - A session that names no provider starts Claude Code, and its run is registered for the log under the provider the lookup found, as for a session that names Claude Code.
  - `deferSpawnUntil`: when a wait ends, a held launch that starts an assistant asks main's launch rule again (`providerLaunchRefusal`). Refused (switched off meanwhile, or the setting cannot be read, or there is no accounts service to ask): nothing starts and the hold on the account is released. Both waits ask, one after the other.
  - A held launch that fails says why in the terminal before the exit, and the window is told of one exit, in each state the session can be in: the process it replaced has ended and left its teardown to the wait (the reason, then that teardown and its exit); that process has still to report its end (the reason at once, and its end sends the exit); the session had no process (the reason, then the start's own exit).
- `src/main/providers/core/accounts-service.ts`: `localLaunchRefusal`, beside `remoteLaunchRefusal`.
- `src/main/ipc/pty-handlers.ts`: an SSH spawn asks the accounts service's `remoteLaunchRefusal` about whichever assistant it starts, and a terminal tab over SSH about the one it names when it names one. With no accounts service the registry's own `session.ssh` declaration answers, so a terminal tab naming Claude Code still opens then. Claude Code declares SSH sessions and Codex does not, so what each is told is unchanged.
- `src/main/ipc/provider-id-schema.ts`: `providerIdSchema`, built from `PROVIDER_IDS`. The three IPC schemas that take a provider id (pty:spawn's options, a Cloud Agent dispatch, the usage filter) use it, so they follow that list. What each accepts is the same two ids as before.
- `src/main/providers/index.ts` re-exports `providerCapability`, the route the launch path already uses to reach the registry.

**Not changed.** The SSH branch of the PTY manager is still untouched: compared with the base (97141019) when this was written, it is the same text, character for character, and so is everything `spawnPtyResolved` runs before it. For an SSH launch `localLaunchFor` answers "none" without asking anything (`pty-ssh-tools-switch-checked` holds it: a provider a local launch is refused for still starts over SSH), and `deferSpawnUntil` is called only from the local branch, so none of the questions above is asked for one. On the shared tail one line differs from the base, the provider a registered run is recorded under, and it is reached only by a run that is registered, which an SSH session never is; the name check there that picks whose saved logging switch applies (`runProvider`) also runs for SSH launches and was left as it was. Of the files the SSH live matrix names, only `src/main/pty-manager.ts` was edited.

**Ratchet.** `tests/unit/architecture/provider-name-ratchet.test.ts` counts, in `src/main` outside `src/main/providers`, comparisons with a provider name and ids defaulted to one, and its header says exactly which spellings those are (equality either way round, case labels, includes / startsWith / endsWith / indexOf / has, named constants whose value is a name; `??`, `||`, `??=`, `||=` and default parameters). Each file has its own ceiling, in `tests/wp1/provider-name-ceilings.json`: a file above either of its numbers fails, as does a file that gains its first check, so a check added in one file is not hidden by one removed in another; a file below a number is asked to lower it. The counts as they stand are 77 comparisons and 32 defaulted ids, and the test states both totals.

**Tests.** Under `tests/unit/main`: `pty-local-launch-registry` (the lookup and its refusals, the rows over `PROVIDER_IDS` and a widened table, an experimental declaration enabled and not enabled through the real accounts service, the shown name in the refusal and a name carrying an escape sequence, a refused launch leaving a running session alone, the run a launch is registered as); `pty-held-launch-provider-off` (the launch rule asked again when each wait ends, and the provider looked up again); `pty-held-launch-replaced-pty` (a refused held launch that replaced a running session: the reason before the exit and one exit, whichever order the two arrive in; a refused launch leaving a held one in place); `pty-spawn-remote-capability` (the question pty:spawn asks for another machine); `ipc-provider-id-schemas` (the three schemas use the shared schema and accept exactly `PROVIDER_IDS`). Under `tests/wp1`: `provider-conformance` asks the real accounts service, over the packages the composition root registers, where each provider's sessions run on win32, darwin and linux (Claude Code on another machine: not refused; Codex: refused by name; either on this computer: not refused); `launch-handoff-pty` runs a Codex launch behind that real service on each platform, directly and as pty:spawn prepares it, and holds that Codex under a copy of Claude Code's row is refused at a launch. Suites that stand in for the accounts service or the session liveness record answer the questions the launch now asks of them.
